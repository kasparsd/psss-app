Creating a vault, and adding a second device

Drawn on 23 Nov 2026 for the new vault format in docs/format.md. Nothing here is built. Technical words (record, log, CloudKit, zone, transport, epoch, key wrapping) never appear inside a device frame; they are explained in this page's prose and in the decisions at the end. The vault is called Personal, the person is alex@example.net, and all data is fictional.

What a first-time person must know here.
  • Which thing? A vault called Personal. It is not a file they have to find. It is kept on the device and, by default, in their iCloud.
  • What must they give? A name (default Personal), one switch (a copy in iCloud, on by default) and a Face ID or Touch ID permission. Nothing asks for a location, a format or a file.
  • Who holds the key? The person, on their devices. Neither Apple nor Psss can open the vault. The recovery kit, a vault password or another device that already has the vault are the only ways back in, and the screens say so before the person commits.
  • Where is it in iCloud? In Psss's own private space in their iCloud. It does not appear in the Files app. Settings lists it as Psss under the Apple Account's iCloud storage. Frames 3 and 4 say exactly this.
  • Can they back up? Yes: the recovery kit is created here, and Save a Backup Copy is in the vault's details (see locations and backup). A copy in iCloud is not a backup, and the screens never call it one.
  • Can they have several vaults? Yes, each with its own locations. The second one is created from the same sheet; the vault list appears only once a second vault exists (locations and backup, section 7).
  • How do they leave? Cancel on every screen before Create Vault leaves nothing behind. After it, nothing is deleted outright; removing a vault is a separate, labeled action.

Dates assume today is 23 Nov 2026. Codes, words and recovery kit characters are made up.

1. Creating the vault

Five frames in order: create, where it is kept, Face ID, the recovery kit, done. The sheet asks for a name and one switch. The facts a newcomer worries about (where it is, who can read it, what if I lose it) are on the screen that needs them.

iPad: follows the Mac layout in a wide window and the iPhone layout in a narrow one. On iPad the create flow is a form sheet, centered, with Create Vault in the bottom button area as on Mac. The recovery kit offers Save and Print through the iPad share and print sheets, and the Face ID line reads Face ID or Touch ID according to the device.

2. A second device on the same Apple Account

The second device signs in to the same Apple Account, opens Psss and finds the vault in iCloud. Finding it is not the same as opening it: the key never travels through iCloud, so a device has to be let in. Approval is done on a device that already has the vault; the recovery kit and the vault password are fallbacks. In the approval frames the new device and the approving device are different platforms on purpose, so both screens are drawn.

iPad: is treated like a Mac or an iPhone depending on width. A new iPad uses the iPhone frames in a narrow window and the Mac frames in a wide one. An iPad that approves shows the request as a centered sheet; the code field accepts the system keyboard's number pad.

3. Errors and edge states

Each frame names the object, says what still works, says what the person can do and never blocks creating or opening a vault for a reason the person cannot fix on the spot.

iPad: uses the same screens. The not-signed-in frame says “This iPad” and points to Settings. The approval request (frame 15 or 16) on iPad appears as a centered sheet. Nothing else differs.

Decisions for the owner

  1. iCloud is on by default whenever the device is signed in to iCloud, and the one switch on Create is the only storage choice.
    Rejected: Off by default with a prompt later; a “where do you want to keep it” picker with iCloud, folder and server.
    Why: The person this is for expects Apple Passwords: every device up to date with no thought. The switch exists for the person who wants a vault that never leaves one device. It is a binary, defaulted choice, which docs/experience.md accepts better than a picker, but it is still the one place where the rule “nothing asks the person to choose where something is stored” bends.
  2. Face ID or Touch ID plus a recovery kit are enough. No vault password is asked at creation; a vault password is an alternative path (“Use a Vault Password Instead…”), not a second thing to set.
    Rejected: Requiring a vault password on every vault (the main source of first-run friction and support load, as docs/experience.md says); Face ID alone with no recovery.
    Why: The format already unlocks with a device key held in the Secure Enclave, so a password is not needed to open the vault on that device. The recovery kit covers the loss case. Pushback on the brief: if I ask the owner to choose “password required”, the first-run goes from three screens to four plus a password that people forget. I recommend keeping password optional.
  3. The recovery kit is offered at creation with Save, Print and a visible Skip for Now, and Setup shows a reminder until one is saved.
    Rejected: Making the kit mandatory before the vault opens; hiding it until Setup.
    Why: Mandatory adds a step to the three-minute budget and trains people to tap through. Hidden means most people never have one and lose the vault with their only device. A skippable screen with a standing reminder is the middle path. A person who skips and loses every device loses the vault, which is the truth the screen states.
  4. The words are “vault”, “recovery kit”, “Where Is It Kept?”, “Ask My Other Devices”, “Approve”, “Decline”.
    Rejected: “Recovery key” (people treat it as a password, and Apple uses the term for its own account recovery); “secret key” (1Password's term); “location” on this first screen (it is vocabulary for the later Setup screens, and a newcomer has not met it).
    Why: Each word is one a newcomer can act on. “Kit” suggests a printed thing to keep somewhere. “Where Is It Kept?” answers the question people actually ask.
  5. A new device is let in by typing the code shown on the new device into the old device, not the other way around.
    Rejected: Apple's own direction (the trusted device shows a code, the new one types it); approval by tapping Allow with no code.
    Why: Typing a code from the new device proves the person is looking at both. Tapping Allow can be done while distracted. The weakness is that a phisher can ask someone to type a code, so the sheet shows what is being approved and says what approving gives. This reverses Apple's direction and is listed under Apple's guidance.
  6. The request lasts 10 minutes and a code works once.
    Rejected: No expiry; 2 minutes.
    Why: Long enough to walk to another room and find a device; short enough that someone who knows the Apple Account password cannot leave a request waiting. That person still needs someone to type the code.
  7. If iCloud is unavailable or the device is offline, Create Vault still succeeds on this device and the screen states the risk and the fix.
    Rejected: Blocking until iCloud is ready; creating silently without saying so.
    Why: People set up apps in a taxi, on an aeroplane and without an Apple Account. A vault that exists is better than a vault that waits, as long as the screen is honest that a lost device then loses it.
  8. The new device's screens do not show device names, and the first one shows no item counts.
    Rejected: Listing “Alex's iPhone, Alex's MacBook Pro” on the found screen.
    Why: Device names are inside the vault, and the new device cannot read it yet. This is a limit of the design, not a taste. The cost is a more generic request screen.
  9. Question: Can the new device show the vault's name (“Personal was found”) before it is let in?
    Drawn as: It shows the name, as the brief asks. If the name is encrypted with the vault, the title would read “A vault was found in your iCloud” and a person with two vaults could not tell them apart until after approval.
    To verify: whether a plaintext vault name in iCloud is acceptable. It leaks a name such as “Family” to anyone with access to the Apple Account's iCloud data. An alternative is a hash of the name shown with a vague label.
  10. Question: Is the recovery kit per person or per vault?
    Drawn as: Per person: the kit says “your vaults”. In docs/format.md recovery adds a wrapped copy of the person key, which would open every vault that person is in.
    To verify: confirm with the owner. A per-vault kit means one printed sheet per vault, which does not fit a person with a Personal and a Family vault. A per-person kit means losing it exposes all of that person's vaults. Both must be said on the kit screen.
  11. Question: Is a vault password needed at all if the system passcode can stand in for Face ID?
    Drawn as: Face ID with a vault password as the alternative. If the passcode fallback of the system authentication works with the Secure Enclave key, the alternative could be dropped from the main path.
    To verify: whether the device key can be released by passcode as well as by Face ID on iOS, and by the login password on a Mac without Touch ID. This would remove a screen and a concept.
  12. Question: Can the old device be told about a request without Psss being open, and can a decline reach the new one?
    Drawn as: A notification and a request sheet on the old device; a declined state on the new device.
    To verify: whether silent pushes from iCloud wake Psss reliably enough to raise a local notification, and whether the new device can read a signed refusal. If not, the old device shows the request only when opened, and a decline looks like a timeout.
  13. Question: Does the iCloud storage list show this space as “Psss”, and can the person see its size?
    Drawn as: Frame 3 and 4 say it is listed as Psss under the iCloud storage of the Apple Account.
    To verify: on a real device. Apple lists app data by app name, but the path and the exact words are from memory, not from a device.
  14. Question: Can the app tell a mistyped recovery kit from a kit that belongs to another vault?
    Drawn as: One message naming both causes.
    To verify: whether a check digit in the kit code is included in the format. If it is, “a character is wrong” can be said alone.

Conflicts with Apple's guidance

  1. A custom screen before the Face ID system prompt.
    The HIG asks for the permission request to appear when the feature is needed, with a purpose string, and discourages pre-permission screens. This screen is the feature's own step (it says what Face ID is for and where the key stays) and has a way out into a vault password, so it is not only a pre-prompt. The cost is one extra tap.
  2. A full-width primary button pinned to the bottom of a form sheet, and a Cancel in the corner.
    The HIG puts sheet actions in the navigation bar. This was accepted on the 23 Nov mocks for the import sheet; it is repeated here for consistency, not re-argued.
  3. The approval code runs from the new device to the old device.
    Apple's own sign-in shows the code on the trusted device and asks for it on the new one. Reversing it here makes the approver look at the new device, at the price of going against what people have learned from Apple. If the owner prefers Apple's direction, frames 13 to 16 swap roles and nothing else changes.
  4. The approval request is an in-app sheet, with a notification as a question.
    Apple's approval prompts use system notifications and full-screen alerts. Psss has no account server to send one, so the request is only as quick as iCloud's push is.
  5. Save and Print as two labeled buttons rather than one Share button.
    iOS would use a share sheet for a PDF. The share sheet hides Print and Save inside a menu, which the project rule against hidden actions rules out here. Both open the system save and print UI.
  6. A waiting screen with a code and no progress bar, with Cancel Request as a plain text button at the bottom.
    The HIG puts Cancel in the navigation bar. The pinned plain button keeps the one action where the eye is. The wait is open-ended, so a determinate bar would be false.
