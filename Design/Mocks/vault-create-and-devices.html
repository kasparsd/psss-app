Creating a vault, and adding a second device

Drawn on 23 Nov 2026 for the vault format in docs/format.md, revised the same day after two decisions by the owner: no password and no recovery kit when a vault is created (the person's key is kept by their Apple Account), and sharing by groups inside one vault. Approved by the owner on 2026-11-23. Not built. Technical words (record, log, CloudKit, zone, transport, epoch, key wrapping) never appear inside a device frame; they are explained in this page's prose and in the decisions at the end. The vault is called Personal, the person is alex@example.net, and all data is fictional.

What a first-time person must know here.
  • Which thing? A vault called Personal. It is not a file they have to find. It is kept on the device and, by default, in their iCloud. Inside it, items can be put into groups to share them (see sharing with a family).
  • What must they give? A name (default Personal), one switch (a copy in iCloud, on by default) and a Face ID or Touch ID permission. No password and no recovery kit. Nothing asks for a location, a format or a file.
  • Who holds the key, and what if it is lost? The person's Apple Account keeps it, protected by their device passcode, the way Apple Passwords is protected. Psss and Apple cannot read the vault. The vault is exactly as safe as the Apple Account and the device passcode, no safer. If the person loses access to the account and made no recovery kit, the vault cannot be recovered. The screen "Where Is It Kept?" says this once, before Create Vault.
  • Where is it in iCloud? In Psss's own private space in their iCloud. It does not appear in the Files app. Settings lists it as Psss under the Apple Account's iCloud storage.
  • A second device? On the same Apple Account the key arrives with the keychain, so the vault is simply there after Face ID or Touch ID. If the key does not arrive, the person lets the device in from another one or with a recovery kit (section 3, drawn as the fallback).
  • Can they back up, and have several vaults? Backup, the optional vault password and the optional recovery kit are in the vault's details (locations and backup). Several vaults are no longer needed for sharing: groups do that.
  • How do they leave? Cancel on every screen before Create Vault leaves nothing behind. After it, nothing is deleted outright.

Dates assume today is 23 Nov 2026. Codes and recovery kit characters are made up.

1. Creating the vault

Four frames in order: create, where it is kept, Face ID, done. The sheet asks for a name and one switch. The facts a newcomer worries about (where it is, who holds the key, what if I lose my Apple Account) are on the screen that needs them, which is the one reached from Where Is It Kept?. A recovery kit and a vault password are not part of creating a vault; they are optional, under Advanced (locations and backup, section 1).

iPad: follows the Mac layout when wide and the iPhone layout when narrow. On iPad the create flow is a form sheet, centered, with Create Vault in the bottom button area as on Mac. The Face ID line reads Face ID or Touch ID according to the device.

2. A second device on the same Apple Account

The second device signs in to the same Apple Account and opens Psss. The key comes with the keychain, so the vault is simply there after Face ID or Touch ID. There is no request, no code and no approval on this path. If the key does not arrive, one waiting state says what to do, and the fallbacks in section 3 take over.

iPad: is treated like a Mac or an iPhone depending on width. A new iPad opens Personal with Face ID or Touch ID exactly as an iPhone does.

3. When the key does not arrive: the fallbacks

These are for a device that cannot get the key through the Apple Account: iCloud Keychain is off, the account is different, or the device is not Apple's. They are secondary, reached from Let In from Another Device… and Use Recovery Kit… on the waiting frame. In the approval frames the new device and the approving device are different platforms on purpose, so both screens are drawn. The kit and password fallbacks exist only for people who made them under Advanced.

iPad: uses the same screens. The approval request on iPad appears as a centered sheet; the code field accepts the system number pad.

4. Creating without iCloud or without iCloud Keychain, and other edge states

Each frame names the object, says what still works, says what the person can do and never blocks creating a vault for a reason the person cannot fix on the spot. The recovery kit is offered here, and only here at creation, because without iCloud, or without iCloud Keychain, nothing else could bring the key back.

iPad: uses the same screens. The not-signed-in frame says “This iPad” and points to Settings. Nothing else differs.

Decisions for the owner

  1. NEW. The vault is exactly as safe as the Apple Account and the device passcode, and no safer. Nothing asks for a password or a recovery kit when a vault is created.
    Rejected: Asking for a vault password at creation; making a recovery kit a required step; a vault password as the default with Face ID on top.
    Why: The owner asked for no passphrase, on the grounds that the key is already behind iCloud's protections. It matches Apple Passwords and removes the largest first-run friction. The cost is stated on the Where Is It Kept? screen and not hidden: the vault is only as safe as the Apple Account. In particular, someone who learns the device passcode and steals the unlocked phone can reach the keychain, and so the key, in the way known attacks on Apple accounts do. A vault password under Advanced is the answer for people who do not accept that.
  2. NEW. The recovery kit is offered at creation only when nothing else could bring the key back (iCloud off, or iCloud Keychain off). Otherwise it is a quiet row under Advanced with no reminder.
    Rejected: Offering the kit to everyone at creation, skippable, with a reminder in Setup (the previous decision); never offering it unprompted.
    Why: It replaces the earlier decision that the kit is offered to everyone with a standing reminder. Pushback on the brief: skipping the kit entirely would be wrong for a password manager if the person has only one device and iCloud off, so that case keeps the offer. For everyone else I would add one quiet line, once, on the Where Is It Kept? screen (it is already there) and no notification. If the owner wants more, the alternative is a single dismissible row in Setup after the 20th saved login.
  3. NEW. What a person without iCloud Keychain sees: a waiting state, then Let In from Another Device or a recovery kit, both secondary.
    Rejected: Blocking the second device until Keychain is turned on; treating the fallbacks as the main path.
    Why: Keychain can be off by choice, or the second device may not be Apple's. The waiting frame says what to turn on, and the fallbacks keep working without a password. A person who has neither another device nor a kit is stuck, which is the same loss as losing the account.
  4. iCloud is on by default whenever the device is signed in to iCloud, and the one switch on Create is the only storage choice.
    Rejected: Off by default with a prompt later; a “where do you want to keep it” picker with iCloud, folder and server.
    Why: The person this is for expects Apple Passwords: every device up to date with no thought. The switch is for the person who wants a vault that never leaves one device. It is a binary, defaulted choice, which docs/experience.md accepts better than a picker, but it is still the one place where the rule “nothing asks the person to choose where something is stored” bends.
  5. The words are “vault”, “group”, “recovery kit”, “Where Is It Kept?”, “Let In from Another Device”, “Approve”, “Decline”. “iCloud Keychain” appears only on the screens that explain it, with what it is.
    Rejected: “Recovery key” (people treat it as a password, and Apple uses the term for its own account recovery); “secret key” (1Password's term); avoiding “iCloud Keychain” altogether.
    Why: No plainer phrase is both true and clear: “your Apple Account keeps the key” is used where a short phrase is enough, and the term is given once, with “Apple's protected store for passwords and keys”, where the person decides. The setting has that name in Settings, so a person who has to turn it on needs the word.
  6. CHANGED. The fallback approval code runs from the new device to the old one, and the request lasts 10 minutes.
    Rejected: Apple's direction (the trusted device shows a code); tapping Allow with no code; no expiry; 2 minutes.
    Why: It was the normal path; it is now the fallback, so the choice matters less. Typing a code from the new device proves the person is looking at both; 10 minutes is long enough to find another device and short enough that someone who knows the account password cannot leave a request waiting. Listed under Apple's guidance.
  7. If iCloud is unavailable or the device is offline, Create Vault still succeeds on this device and the screen states the risk and the fix.
    Rejected: Blocking until iCloud is ready; creating silently without saying so.
    Why: People set up apps in a taxi, on an aeroplane and without an Apple Account. A vault that exists is better than a vault that waits, as long as the screen is honest that a lost device then loses it.
  8. The new device's fallback screens do not show device names, and the vault's name is shown only once the key has arrived.
    Rejected: Listing “Alex's iPhone, Alex's MacBook Pro” on the waiting screen.
    Why: Device names and the vault's name are inside the vault, and a device without the key cannot read them. On the normal path the key has arrived, so the name is shown.
  9. Question: Does Psss need a vault name at all now that sharing is by groups?
    Drawn as: Create still asks for a name, default Personal, as the owner saw it.
    To verify: with the owner. Names mattered when several vaults were the way to share. With groups, one vault per person is the norm, and dropping the field would leave Create with one switch. “Only Me” is the group that is always there.
  10. Question: Can Psss tell that iCloud Keychain is off, and can its key be kept there at all?
    Drawn as: Frame “iCloud Keychain is off” assumes the app can tell.
    To verify: whether the app can read the state of the setting or only fails to store the key, and that a synchronizable keychain item for the person key survives Advanced Data Protection settings and Apple's own account recovery. The format is not tied to it, since the key is one more wrapped copy.
  11. Question: When Face ID is declined or fails, what opens the vault?
    Drawn as: Not Now on the Face ID screen. The caption says the device passcode.
    To verify: whether the device key can be released by passcode as well as by Face ID on iOS, and by the login password on a Mac without Touch ID. If it cannot, the vault password becomes the alternative again, under Advanced.
  12. Question: Is the recovery kit per person or per vault?
    Drawn as: Per person: the kit is for Alex. In docs/format.md recovery adds a wrapped copy of the person key, which would open every group that person is in.
    To verify: confirm with the owner. Losing the kit then exposes every group the person belongs to. The kit screen must say so.
  13. Question: Can the old device be told about a request without Psss being open, and can a decline reach the new one?
    Drawn as: A notification and a request sheet on the old device; a declined state on the new device.
    To verify: whether silent pushes from iCloud wake Psss reliably enough to raise a local notification, and whether the new device can read a signed refusal. If not, the old device shows the request only when opened, and a decline looks like a timeout. This now concerns only the fallback.
  14. Question: Does the iCloud storage list show this space as “Psss”?
    Drawn as: The where-it-is-kept screen says it is listed as Psss under the iCloud storage of the Apple Account.
    To verify: on a real device. Apple lists app data by app name, but the path and the exact words are from memory.
  15. Question: Can the app tell a mistyped recovery kit from a kit that belongs to someone else?
    Drawn as: One message naming both causes.
    To verify: whether a check digit in the kit code is part of the format. If it is, “a character is wrong” can be said alone.

Conflicts with Apple's guidance

  1. A custom screen before the Face ID system prompt.
    The HIG asks for the permission request to appear when the feature is needed, with a purpose string, and discourages pre-permission screens. This screen is the feature's own step and has a way out, so it is not only a pre-prompt. The cost is one extra tap.
  2. A full-width primary button pinned to the bottom of a form sheet, and a Cancel in the corner.
    The HIG puts sheet actions in the navigation bar. This was accepted on the 23 Nov mocks for the import sheet; it is repeated here for consistency, not re-argued.
  3. In the fallback, the approval code runs from the new device to the old device.
    Apple's own sign-in shows the code on the trusted device and asks for it on the new one. Reversing it makes the approver look at the new device, at the price of going against what people have learned from Apple. If the owner prefers Apple's direction, the two approval frames swap roles and nothing else changes.
  4. The approval request is an in-app sheet, with a notification as a question.
    Apple's approval prompts use system notifications and full-screen alerts. Psss has no account server to send one, so the request is only as quick as iCloud's push is.
  5. Save and Print as two labeled buttons rather than one Share button.
    iOS would use a share sheet for a PDF. The share sheet hides Print and Save inside a menu, which the project rule against hidden actions rules out here. Both open the system save and print UI.
  6. A waiting screen with no progress bar, with Cancel Request as a plain text button at the bottom.
    The HIG puts Cancel in the navigation bar. The pinned plain button keeps the one action where the eye is. The wait is open-ended, so a determinate bar would be false.
