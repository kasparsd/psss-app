Password generator

Mock for approval, drawn on 23 Nov 2026. Awaiting approval: nothing here is built, and no document has been changed to match. The plan behind it is docs/plans/password-generator.md. This page was written without a browser and was checked by reading the markup back, not by viewing it rendered. Check it in a browser, in light and dark, before approving.

The recommendation in four lines.
  • The default is six words, each capitalised, joined by hyphens, with one number: about 83 bits, 48 characters, easy to read and type. It is not called the safest. It is the strongest password that a person can read aloud or type on a TV.
  • The site’s rules are met without comment. Only when they force a change of kind (a 16 character cap) does one plain line say so.
  • One control, the same in the editor, the AutoFill sheet and Setup: Words, Numbers, Symbols and a labeled Customize. Changes are remembered per device. A site’s rules are remembered with its login.
  • One tap on Use This Password and one Face ID glance fill the page and save the login first, so it is never lost.
What a first-time person must know here.
  • What is being made? A new password for one site. It is shown before anything is saved or filled.
  • Where does it live? Only in the vault on this device once they press Use This Password. Nothing is uploaded and an unused password is never stored. The sheet says so in one line.
  • Who holds the key? Face ID opens the vault to save the login. Showing the suggestion needs no unlock, because it reads nothing from the vault.
  • How do they get out? Cancel, always visible. Nothing is saved or filled. If the site says no, one button, The Site Didn’t Accept It, and one answer make a password that fits.
  • What happens next? The button names it: Use This Password fills the site’s fields and saves the login.

Every password on this page is invented. Strength sentences use one trillion guesses a second against a site that stored the password badly, which is a deliberately pessimistic assumption. Numbers come from the plan, which says which were computed and which are secondary-sourced.

1. In the app: a new login, and changing a password

iPad: regular width uses the Mac sheet, compact width the iPhone form. Dynamic Type at the largest size keeps the preview on several lines and moves the three buttons under each other. The preview is hidden when the app is not active and while the screen is being shared, and then reads “Hidden while the screen is being shared.”

2. A site asks for a new password (iPhone and iPad, iOS 26.2 or later)

Mac has no system request for this. Its frames show the bundled Safari extension’s popup, which uses the same card. What the system and our code do today, and the table of save events, are in the plan (section 3b). Taps for the normal case: focus the password field, tap Use This Password, one Face ID glance.

iPad: the sheet is the iPhone sheet at medium height, a form sheet at regular width. If the system calls us without UI instead, it shows its own list of up to three passwords from us (words, characters with a symbol, letters and digits), in that order, each satisfying the rules. After the person picks one, the filled-event save writes the login with no question. I could not verify the system’s own list on a device.

3. No generate request: below iOS 26.2, some apps, and everything on Mac outside Safari

Psss cannot see the page, so it cannot fill it. What we honestly offer is the editor’s card with a labeled Copy Password. The login is stored as a draft first, so leaving to paste does not lose it. There is no save-after-submit prompt on Mac (no API), and the caption says so once instead of apologising.

5. Choices that are yours

A. The default

A1. Words only
Wake-Stoop-Zoology-Everyone-Unsure-Tipped
77.5 bits, 41 characters. About 3,500 years at a trillion guesses a second.
Letters and digit rules of the awkward sites: passes 15% of them. Closest to “just multiple words”.
A2. Words and one number (recommended)
Reclusive-Slam7-Justness-Gore-State-Balcony
83.1 bits, about 48 characters. About 160,000 years.
Passes 48%. The number adds about 5 bits and is the cheapest thing that makes most sites accept it first time. Capitals and hyphens are free.
A3. One number and one symbol
Claim-Sinner9-Deafness-Embroider!-Latter-Alibi
88.7 bits, 46 characters. About 8 million years.
Passes 53%. Five more points of compatibility for a keyboard switch on every sign-up. Not worth it as a default; one tap on Symbols gives it.

Percentages are a simulation over Apple’s list of 471 sites with known rules, which is a list of awkward sites and not the web at large. Length matters more than any of the three: 35% of those sites allow at most 16 characters, and the generator switches to random characters for them.

Decisions for the owner

  1. The default is six words with capitals, hyphens and one number. It is called easy to read and type, not safest.
    Rejected: Words only (passes 15% of awkward sites); numbers and a symbol (5 points more compatibility for a keyboard switch); five words (70 bits, no margin over Apple’s 71); seven or eight words (past many sites’ length caps).
    Why: Six words are 77.5 bits and the number lifts it to 83, above Apple Passwords’ 71. Per character words are weak, so random characters are the better fit when a site caps length, and the interface does not claim words are safer.
  2. The site’s rules are met silently. One plain line appears only when the kind had to change or the words were reduced.
    Rejected: Always showing the rules; asking the person which rule to relax.
    Why: People do not know Apple’s rule language and cannot decide anything useful. The line names the cause (a maximum length) because a different-looking password would otherwise be a surprise.
  3. The controls are Type (Words or Random characters), Words, Numbers, Symbols and, behind More Options, Separator and Capitalize. In Random characters, Length replaces Words.
    Rejected: Avoiding look-alike characters as a switch (always on); a custom symbol set; pronounceable passwords; a word list or language choice; a minimum-length slider; a coloured strength bar.
    Why: Each rejected control is a decision the owner’s family should not have to make. The fixed symbol set is the one most required-symbol rules accept in Apple’s list. English words only: sites’ password fields are ASCII on most of the web and a TV or console keyboard may not type Latvian letters.
  4. Changes are remembered as the new default at once. Reset to Recommended appears only when they differ.
    Rejected: A “Use as default” switch (a second decision on every use); a Save button on the card.
    Why: One memory and one way back. A change a site forced is never remembered as a preference.
  5. The defaults are per device, in the shared App Group defaults, read by the app and the extensions. The owner may prefer them with the vault (section 5B).
    Rejected: Storing them in the vault: it needs Face ID before the AutoFill sheet can show a suggestion and a change to the vault format for a setting few people change.
    Why: The sheet must appear without an unlock, because generating reads nothing from the vault. The recommended settings are what most people use on every device.
  6. A site’s rules are remembered with its login, as a hidden field (a KDBX custom data item named PSSS_PASSWORD_RULES while the store is KDBX). Forget removes it.
    Rejected: A visible custom field (other apps would show it and a person might edit it); a global list of sites (it would be a second place that leaks where the person has accounts).
    Why: It is the site’s rule, not a secret, and it makes “change password” work first time. It stays with the item when the item moves between vaults or is exported.
  7. In AutoFill, Use This Password unlocks, saves the login, and only then returns the password to the page.
    Rejected: Returning it first and saving on the later submit (a closed page loses the password); asking for a title or a vault; a confirmation after the fill.
    Why: A generated password the person never saw twice must never be the only copy. The header’s own guidance for the filled event is to save as pending and ask nothing. The cost is a stray login if the sign-up is abandoned; it can be deleted with Undo.
  8. The recovery is a button, The Site Didn’t Accept It, with three answers in the words sites use.
    Rejected: One “Make it simpler” button stepping through presets (covers about two thirds of the awkward sites and never explains); sending the person to Customize (an expedition, and most of them cannot name the rule).
    Why: The person has the site’s error in front of them and can match it to one of three phrases. Each answer adds one rule to the same engine the request’s rules go through, and that rule is remembered with the login once it is saved.
  9. The no-request fallback is the editor card with a labeled Copy Password that saves a draft first.
    Rejected: A promise of save-after-submit on Mac (no API); a floating generator window; copying silently.
    Why: Honest about what Psss cannot see. The draft means switching apps to paste does not lose the login.
  10. Setup gets one row, Password Generator, which opens the same card.
    Rejected: A settings screen of its own with separate controls (a second interface to keep in step); no row (nowhere to see what the default is).
    Why: One control, one place to learn it, and the row shows the current value. It adds one row to Setup, which stays under ten.
  11. The preview is visible without a gesture, and hidden when the app is inactive or the screen is being shared.
    Rejected: Hidden until Show (the person must read it to type it on a TV, and would tap Show every time); a Hide control.
    Why: The suggestion is new and unsaved. This is a narrow exception to the secrets rule, listed below.
  12. No history of unused passwords, no pending marker, no usernames or aliases.
    Rejected: Bitwarden-style generator history.
    Why: A history would be a plaintext store of secrets the person never kept. The saved login’s Previous passwords is the only history.

Conflicts with Apple’s guidance

  1. Two filled buttons on the Mac sheet (Use This Password inside it, Save below).
    Apple’s guidance is one default button per sheet. The card is a control inside the form, not the sheet’s confirm action, and the project rule is a visible, labeled action. The trade-off is a screen with two prominent buttons; the alternative is to let Use This Password be a bordered button on Mac only, which is a cheap change if the owner prefers it.
  2. The password is on screen without a gesture.
    This is a project rule (secrets are never visible without a deliberate gesture), not Apple’s. Apple Passwords and every manager show a generated password. It is hidden while the app is inactive and while the screen is shared, which are the cases a bystander or a recording could see.
  3. A labeled button in the content instead of a toolbar symbol.
    Apple would put Generate in the top trailing position of the sheet. The project rule is visible, labeled actions. The cost is a taller sheet.
  4. Steppers and a segmented control, not a slider and a menu.
    This follows the HIG: steppers for small counts, a segmented control for two choices. Listed because the owner asked for “number of numbers” and a stepper is the standard way. A slider would hide the exact count.
  5. On Mac the popup is Psss’s own.
    macOS has no system generate or save prompt for a provider (confirmed in the SDK headers). The extension’s popup is the only route in Safari; other browsers and apps get the editor card.
  6. The extension sheet follows the header’s rules.
    Cancel is always visible, as the header requires, and no vault data is read before Face ID.

What it needs from the code

  • A new generator in App/Core/PasswordGenerator.swift with an injected random generator, a parser for Apple’s Password Rules language, a generated word list (EFF long list, four hyphenated words removed, attribution), and a settings value in the shared defaults. Today’s generator ignores rules and can fail to include the characters it promises.
  • The provider reads passwordFieldPasswordRules, confirmPasswordFieldPasswordRules and passwordRulesFromQuirks, returns up to three results, implements prepareInterface(for:) for generate (or sets SupportsGeneratePasswordCredentialsWithUI to false until it does), and handles the save event generatedPasswordFilled without a question.
  • A pure function for the pending-login matching so the event table can be tested without a host.
  • One SwiftUI card used by the editor, the sheet, Setup and the Mac extension’s popup; a hidden passwordRules field on a login.
  • Platform facts not yet verified on a device: what the system shows when several results come back; how a person starts the user-initiated sheet; what a native app’s request carries; whether Safari turns length attributes into rules; and what happens to a filled-but-unsubmitted form when the page closes.

Deliberately not built

  • A history of generated passwords.
  • A marker or reminder for a login saved before the site accepted it.
  • Usernames and email aliases.
  • Pronounceable passwords, custom symbol sets, a choice of word list or language.
  • Strength checks on passwords the person types.
  • Settings that travel with the vault (option B, if the owner prefers it).
  • A save-after-submit capture on Mac.
