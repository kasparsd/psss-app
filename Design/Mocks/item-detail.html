Item detail additions

Mock for approval. Nothing here is built. These are the sections at the bottom of a login's page: other fields and attachments for imported items, previous passwords, and the two passive dates. The page above them (website, username, password, notes) is the one in the app today and is drawn only for context. The Mac frames hide the sidebar so the detail column has room; with the sidebar open the same rows simply get narrower.

What a first-time person must know here.
  • Which thing? Extra information that came with an imported or existing item: fields Psss has no editor for yet, attached files, the passwords the login had before, and when it was added and last edited.
  • Where is it stored? Inside the same encrypted vault file. Attachments are never opened or decrypted anywhere else unless the person chooses Save…, which says the copy is not encrypted.
  • What can they do? Show or copy any hidden value, save an attachment, restore an earlier password, clear the old passwords.
  • What can go wrong? A restore or clear is refused because the file changed elsewhere: the existing conflict alert (page 4).
  • How do they get out? Restore is its own undo, since the password it replaced joins the list. Clear is the one irreversible action and asks first.
  • Unbuilt, so not promised: editing, adding and removing other fields and attachments, and tags. The footers say “cannot edit them yet”.

1. A login with everything

iPad follows the Mac layout in a wide window (one-line rows with buttons on the right) and the iPhone layout in a narrow one (buttons under the value). The confirmation is a popover anchored to “Clear Previous Passwords”. Save… opens the system file saver on iPhone and iPad and a save panel on Mac; the mock draws neither.

Decisions for the owner

  1. Order at the bottom: Other fields, Attachments, Previous passwords, then the dates, always last.
    Rejected: Dates under the header (they would sit beside the actions people use most, against items.md). Previous passwords above Other fields (it is the more useful section, but only some logins have it, so the stable sections go first).
    Why: items.md says the dates are the last section and never beside an action; the rest follows how often each appears.
  2. Previous passwords are shown by default, with every value hidden, whenever an earlier different password exists.
    Rejected: Collapsed behind a disclosure row (hides Restore, the safety net when an AutoFill update saved a wrong password). Off by default in a setting (adds a setting for a safe default, against the experience doc).
    Why: A hidden value is no more exposed than the main password. The section is absent when empty, so most logins never see it.
  3. Restore is one tap with no confirmation.
    Rejected: Confirm first. Restore only after Show.
    Why: It is undone by Restore on the row it created. A message names what happened.
  4. Clear Previous Passwords always confirms, names the item and count, and says backup copies may still hold the passwords.
    Rejected: No confirmation (irreversible). A switch to turn history off (a feature, not a screen).
    Why: Irreversible, and the privacy sentence in items.md must not promise more than the code does.
  5. New rows use labeled text buttons (Show, Copy, Restore, Save…). Notes: today's rows use a quiet copy glyph.
    Rejected: Copy as an icon like the existing rows, Restore in a menu.
    Why: AGENTS.md and the experience rules want visible labels. This makes the new sections visibly different from the current rows; decide whether to relabel the current rows too.
  6. Other fields and attachments are read-only, and the footer says so in one sentence.
    Rejected: Hide them until editing exists (the imported data would be invisible, which is why the plan wants them). Show them as editable and fail on save.
    Why: The import plan says data that is intact in the file is useless until it can be seen. Not promising an editor keeps the copy true.
  7. Dates are absolute and use “Added” and “Edited”.
    Rejected: Relative (“3 days ago”): goes stale and reads badly in VoiceOver. “Created” and “Modified”: file words.
    Why: items.md. “Added” stays true for imports.
  8. The Edited date moves after Restore and after Clear Previous Passwords.
    Rejected: Leave it unchanged for Clear.
    Why: Both write the entry. The codec stamps the modification time on Clear on purpose so a merge cannot bring the history back. The page does not call it an edit of the content, so I would accept it; flagging it because “Edited” may surprise someone.
  9. Cards, secure notes and custom items get Other fields and Attachments, but never Previous passwords.
    Rejected: Previous passwords on custom items that hold a secret.
    Why: History of the password field is only defined for a login. Revisit after the field model.

Conflicts with Apple's guidance

  1. Section headers and footers at body size, not the smaller grouped-list style.
    The project rule is two sizes. The trade-off is less visual separation between a header and the row under it; secondary colour does that job.
  2. Several buttons in one list row (Show, Copy, Restore).
    HIG discourages more than one tappable control per row because targets get small and compete with the row's own action. Here the rows have no row action of their own, each button is a capsule of at least 44 pt tall in the real build, and the iPhone layout puts them on their own line. The alternative, a menu behind an ellipsis, breaks the rule that important actions are not hidden.
  3. Destructive “Clear Previous Passwords” as a plain red row.
    This follows Apple's grouped-form idiom. It does not repeat the red inside the confirmation as a filled button, which is also the HIG form.
