Command line

Part 1, the core command: approved by the owner on 2026-11-24, not built. Part 2, agent access, proposed 2026-11-23: not approved, not built. The open questions under each part still stand. The reasoning, the prototype and what it measured are in docs/cli.md. Part 1 prints text in a terminal, on macOS, Linux and Windows, and is the priority. Part 2 adds sheets in the Mac app, so it is Mac only: iPhone and iPad have no command line, so nothing in part 2 appears there.

The four questions below are answered for the agent sheets of part 2. The core command’s four are answered under the Part 1 heading.

  • Which thing? A program on this Mac (a terminal, a script, an AI assistant such as Claude) asks Psss to use one named item from the vault. The sheet names the app that asked, the item, and what will be done with it.
  • What must they give? One choice (not at all, this once, or until Psss locks) and Touch ID. Nothing is typed.
  • What can go wrong? The asker wants an item that does not exist, there are two with that name, or it wants to send a password to a website it was not saved for. Each has its own sheet below.
  • How do they leave? Don’t Allow. Later: Setup lists what is allowed and has Stop Allowing; locking Psss forgets all of it. Nothing in the vault is changed by allowing or refusing.

Part 1 · The core command in a terminal

Added 2026-11-24. This is what psss prints for a person or a script when it opens a vault folder itself with its own key (direct mode). Ordered the way a first day goes: create a vault, check it, put a secret in, take it out, use it, then what goes wrong. Frames are terminals only; nothing here is a sheet. All data is fictional.

  • Which thing? A vault: a folder of encrypted files with a name, kept where the person says, opened with a key file on this computer. Every message names the vault and the file it means.
  • What must they give? A name for the vault when it is made, and a secret's value on standard input or typed without echo. Never a key or a value as an argument.
  • What can go wrong? A name that matches two items or none, a missing key file, a location that fell behind, a record that was changed. Each has its own words and an exit code a script can read.
  • How do they leave? Nothing is ever deleted without a confirmation, a dry run exists for everything that writes in bulk, and a KeePass copy of the whole vault can always be written out.

Decisions to approve for the core command

  1. The first output says what was made, where, who holds the key and what loses it. Rejected: one line, “Created Personal”. Why: a key file is the only way back, and the person should learn that before they put anything in, not when it is gone.
  2. init offers a way back and never forces one. In a terminal it asks; in a script it warns on standard error and exits 0. Rejected: refusing to finish without a recovery kit or password; making a kit silently. Why: a script must be able to create a vault, and a kit nobody asked for is a secret nobody knows about.
  3. A value is never an argument. set reads standard input or asks without echo. Rejected: a --value flag. Why: arguments show in process lists and shell history.
  4. get prints the bare value. Rejected: a label, a colour or JSON by default. Why: so a variable or a file gets exactly the value. Structure is --json.
  5. A title matches only exactly, ignoring case. Two items with one title are listed by id and exit 3; a near miss exits 3 with hints that are never used. Rejected: prefix matching; taking the first or the most recent. Why: if the item a script meant is deleted, a prefix match quietly returns another item’s secret. The wrong secret in the wrong place is worse than one more command. Scripts that must not break on a rename use the id form.
  6. One table of exit codes, the same in both modes. 0 done, 1 failed, 2 wrong use or a failed check, 3 no such item, an ambiguous name or not allowed, 4 locked, not open or no key. Why: the agent frames below already use 3 and 4 this way, and a script should not learn two tables.
  7. Every error says what is wrong and what to do; an error about a vault names the vault and the file. Rejected: “Permission denied”, “Invalid key”. Why: the person has not read this repository.
  8. verify reports and never repairs. Why: a repair would be a write made by a tool that has just found something wrong.
  9. The key file is one file per vault in the user’s config folder and never inside the vault folder. init refuses a key file inside the vault. Rejected: one device.key for every vault; a key next to the vault. Why: the format uses a device key for one slot only, and a key beside the vault would travel with it through iCloud Drive or Dropbox.
  10. init offers only ways back that exist. The recovery kit joins the list when key kit is built and mocked. Rejected: listing options that end in “not built yet”. Why: a promise that depends on an unbuilt feature reads as a failure.
  11. set on a title that does not exist fails unless --create is given; rm asks nothing. Only permanent purge asks. Rejected: set adding items silently; rm asking y/N. Why: a typo in a title would add a stray item; rm moves to Recently Deleted and restore undoes it.
  12. Reading warns and never refuses. If opening the vault found a problem (a record that fails its checks, a gap, a location that looks rolled back), get, list and set print one plain warning on standard error and keep their exit code. A key file other users can read gets its own warning. Rejected: refusing to read; saying nothing. Why: a vault that is only behind must stay readable, and a stale value with no word is the worst outcome. verify says what is wrong.
  13. status uses the words of the app: “Kept in”, “Up to date”, “Behind”, “way back”. Why: one meaning each, on every platform.
  14. A write that could not be delivered still exits 0 and says so (A12; built, words awaiting approval). A warning on standard error after the result, status shows Behind with a count, sync delivers, and --json carries delivery. Rejected: exit 1; saying nothing. Why: the change is stored here and a retry would write it twice; a script that must know reads --json or runs sync, which exits 1 while a location is unreachable. Silence left a change late with no word.
  15. search, history and code print for a person what the apps show, and never a value unless asked (A13 to A15; built, words awaiting approval). search reads name, username and website like the apps; history shows fields and dates and gives earlier values only with --show; code prints the code and the seconds left only at a terminal. Rejected: searching notes, tags or values; showing earlier values by default; a countdown or --watch; a “code” that is a stored field. Why: a search result or a history is pasted into chats and logs, so what it shows must be what the apps already show openly; a value takes a flag that says so.

Open questions for the core command

  • Where does a new vault go when no place is given? A1 assumes ~/Psss on macOS. Linux and Windows need their own default.
  • Does init ask for the name when it is left out, in a terminal?
  • Is “way back” the right phrase on the command line, or do “recovery kit” and “vault password” stand alone?
  • What a printed recovery kit looks like, and whether key kit prints to the terminal or writes a file. It is the next frame to mock, before key kit is built.
  • What a KeePass export leaves out. A9 names only the people in shared groups; the full list depends on the mapping in docs/items.md and the history question in the vault format.
  • Whether list should show field names at all when the terminal output may be pasted into an AI conversation. They are names, not values, but they say what is stored.

Decisions to approve

  1. The app asks, the command holds nothing. The psss command has no key and cannot open a vault; it passes the question to the running app. Rejected: a command that unlocks the vault itself with the vault password or a saved key. Why: a key the command can reach is a key any script can reach, and there would be two things that open a vault.
  2. Touch ID confirms, not a click. Rejected: a plain Allow button. Why: an assistant that can control the screen can click a button. It cannot give a fingerprint.
  3. Neither Allow is the default button. Return does nothing. Rejected: Allow Once as the default. Why: these sheets appear while the person is typing elsewhere, and a stray Return must not answer one. Departure from Apple’s guidance, listed below.
  4. Three lengths only: not at all, once, until Psss locks. Rejected: “Always”, timers (10 minutes, 1 hour), a per-item switch. Why: “until it locks” needs no explaining and ends by itself; an “Always” for an assistant is an open door that outlives the reason for it. Can be revisited with evidence of real fatigue.
  5. “Until Psss locks” is offered for sending to a website and for verification codes, and covers what the sheet showed: the app that asked, one field of one item, and one request (its method, address and how the secret is sent; the query, the contents sent with it and other headers may differ). Rejected: allowing an app to use an item for anything. Why: each sheet should mean one thing the person can picture.
  6. Running a program is asked for every time. Rejected: keeping it per program; keeping it per exact command line; a list of “shells” that are treated differently. Why: all three were built and tested. With “this program” kept, git and find were given new arguments. With “this exact command” kept, the same command was made to do something else through settings around it that no sheet can show. The cost is more sheets for people who use run often.
  7. A program asks for one item by name and never gets a list. psss list shows only what was allowed. Rejected: search over titles; a group of items marked “for the command line”. Why: titles alone say where someone banks, and an assistant’s whole conversation leaves the Mac. The person tells the assistant the name.
  8. A wrong name, a refusal and a missing field look the same to the asker, and a wrong name still shows a sheet. Rejected: “no such item”. Why: otherwise names can be guessed one by one.
  9. A password is sent only to the website it is saved for, with no override on the sheet. Rejected: a “Send Anyway” button, as the browser popup has. Why: here the address comes from a program, not from a page the person is looking at.
  10. Seeing a value is a separate, louder use, asked every time, and the command refuses it outside a terminal unless told. Rejected: no way to print at all. Why: a person at a terminal legitimately wants it, and without it people would paste from the app, which is worse.
  11. Off by default, in Setup, Mac only. One switch; it counts against the ten-settings budget. Why: most people never need it, and a closed door needs no trust.
  12. What is allowed and what happened are kept on this Mac only, never in the vault and never synced. Why: they describe this Mac’s programs, and a synced record of where each token was used is itself sensitive.

Departures from Apple’s guidance

  • No default button on the sheets in section 1. The guidelines prefer a default button for the likely choice. Trade-off: one more deliberate click, in exchange for a sheet that a stray Return cannot answer. Same choice as the invitation sheet in family sharing.
  • Three buttons with long labels. Within the guideline’s limit of three, but “Allow Until Psss Locks” is long. Alternative if it reads badly in the app: two buttons and a “Keep allowing until Psss locks” checkbox.

Open questions

  • What name is shown when no app is found in the chain (a remote login, a background job)? Proposed: “A program on this Mac”, with the program’s file path, and no “until Psss locks”.
  • Should several items wanted by one command share one sheet? The prototype asks once per item.
  • Does a new login from an assistant always go to Only Me, as logins from Safari do?
  • Does the activity list belong in Setup, or on each item (“Used by Claude today”)?
  • How the psss command reaches Terminal from a Mac App Store app is not known yet (spike S5). 3b assumes it is simply there.
