Fill a login

Drawn 24 Nov 2026 from the code as it is today, with three marked departures that are not built. Strings are copied from Extensions/CredentialProvider, App/Core/FillSite.swift, SiteMatch.swift and PasskeyRequestList.swift, so the owner can see the whole flow in one place and change it. The departures: (1) a suggestion fills straight after Face ID, with no “Fill” screen (owner decision; the app still shows the screen today); (2) “Other Logins…” is called “Find Another Item…” and its rows open an item instead of filling at once; (3) section 4, the owner’s request to search any item and choose which value to use, which is entirely new. Everything else is as built. The system’s own pieces (the suggestion above the keyboard, the Face ID prompt, the AutoFill menu) are not ours and are drawn only as far as I know them. Not viewed on a device.

0. What a first-time person must know

  • Which thing? One login saved in Psss, put into the sign-in page the person is looking at. Psss offers only logins saved for that site. Others sit behind a labeled step with a confirmation.
  • What must they give? Face ID or Touch ID, once per fill. If more than one login fits, one tap to choose.
  • What can go wrong? Nothing is saved for this site; Face ID is cancelled or was turned off; the vault file cannot be found or opened; the page is not encrypted; the page is not the site the login was saved for.
  • Where does it live? The logins stay in the vault on this device. Nothing is sent to a server. The page receives only the one login the person chose.
  • How do they leave? Cancel on every screen. The page is left as it was and nothing in the vault changes.
  • What happens next? The email and password fields are filled. The person presses the page's own sign-in button; Psss never submits the page.

4. Find any item, then choose what to use

Added 24 Nov 2026 at the owner's request. A service changes its sign-in address and the saved login no longer matches. The person should not have to edit the item before it works: they search the whole vault from the popup, open the item and choose which value goes in. Psss never changes the item for them here.

5. Another site, or a page that is not encrypted

One sheet of Psss’s own, on iPhone, iPad and Mac. Cancel is the default and answers Return; Fill Anyway is a plain button, not red, because continuing is not a deletion. Values from the vault are in quotes and site names are not, so one cannot pass for the other.

7. Verification codes

A code is offered only for logins that have a readable code and belong to the site. There is no “Find Another Item” for codes, by design: a code for the wrong site is worse than none.

Decisions for the owner

  1. Psss fills only logins saved for the page’s site, and the rest sit behind “Find Another Item…” and a confirmation naming both sites.
    Rejected: Listing every login (one tap away from filling a bank password on a lookalike page). Hiding other logins entirely (a login saved under a different address could never be used).
    Why: the confirmation names both sites, so the person sees the mismatch. This is as built.
  2. The popup searches the whole vault, and a result opens an item instead of filling it (owner, 2026-11-24).
    Rejected: asking the person to edit the item's site first (a changed address would stop them signing in until they found the item in the app). Searching only logins by name and account (the old address is what they remember). Filling the whole login at the first tap on a result (no way to use one value).
    Why: a service that moves its sign-in must not turn the vault into a locked box. Search covers name, account and saved site, over logins and custom items. Cards and notes are left out (open question 3).
  3. The item screen offers the whole login first and single values below it, with Use where the system inserts and Copy where it cannot (owner, 2026-11-24).
    Rejected: only single values (two taps and two popups for the common case). Hiding single values behind a menu (a person who needs one would not find it).
    Why: the first button is what a changed address needs; the rows answer the “which value” request. The verb names what happens: Use inserts, Copy copies.
  4. The item screen carries the two sites and is the confirmation (7). Recommended; the owner decides.
    Rejected: a separate “Fill a login from another site?” sheet after the choice (a third screen, and the two sites would be read twice). Hiding the sites on this screen and asking only after (the choice would be made before the person has seen the mismatch).
    Why: the decision and the facts are on one screen. Cost: it breaks today's rule that Cancel is the prominent default, because there are several actions. Back is the way out, and nothing fills on a stray tap on a row because each row's action word is visible. The http line is shown on this screen too.
  5. Psss never changes the item from here.
    Rejected: adding the new site to the login automatically (anything the person finds could be tied to a lookalike page by one tap).
    Why: filling and editing are different acts. A later offer to remember the site is open question 2.
  6. Cancel is the default on the confirmation; Fill Anyway is plain, not red.
    Rejected: a system alert (cannot make Cancel both the Return default and the Escape button).
    Why: as built; continuing is not a deletion.
  7. A suggestion fills straight after Face ID, with no confirmation screen (owner, 2026-11-24).
    Rejected: a “Fill” screen after Face ID (it repeated the name and account already in the suggestion the person tapped, and Apple Passwords fills straight away). A confirmation stays only where it adds a fact the person cannot see: another site, or an unencrypted page, both on the list path (frames 13 and 14). The suggestion path cannot meet either case: the system gives only the stored domain with it, and the release check refuses a login whose site does not match.
    Why: one fewer tap on the most common fill, and no screen that only restates what was just chosen. Not built: FillConfirm and its use in prepareInterfaceToProvideCredential go away (see “What it needs from the code”).
  8. Face ID before any list, even an empty one.
    Rejected: showing “No logins are saved” before Face ID (leaks that nothing is saved without proving who is asking).
    Why: as built; the vault has to be opened to know.
  9. The sample vault is never offered to AutoFill.
    Rejected: filling sample logins (they are fake and would fill real pages with fake passwords).
    Why: as built (“No vault yet”).
  10. Nothing about AutoFill being off is shown here.
    Rejected: a message from the AutoFill sheet (the sheet never runs while AutoFill is off).
    Why: the reminder card has to do it, before the person leaves the app.

What it needs from the code

  • Find an item and its fields (new, proposed): a pure search in App/Core (name, account, saved site; logins and custom items; A to Z; the count for “Showing 40 of …”), and a pure field list for an item (label, a safe preview, whether it is secret), both with hostless tests. The provider's others list is replaced by them.
  • ProvidesTextToInsert in the provider's Info.plist, prepareInterfaceForUserChoosingTextToInsert (iOS 18, not Mac) and completeRequest(withTextToInsert:) for Use. On Mac, and wherever insertion is refused, the clipboard with the concealed, 60-second rules already used for item copies.
  • ReleaseCheck gains a per-field release: the one chosen value, nothing else, and the other-site facts computed the same way as the old sheet.
  • In CredentialProviderViewController.prepareInterfaceToProvideCredential(for: ASPasswordCredentialIdentity): after the release check, call complete(with: item) directly instead of presenting FillConfirm. Remove FillConfirm from ProviderViews.swift if nothing else uses it (the passkey and code identity paths do not).
  • Keep the release check (ReleaseCheck.password): it is what makes skipping the screen safe. Add a check that a login whose site does not match the identity is refused with no screen (K2 covers the rule; the wiring is the gap).
  • Frames 1 to 3 and F2 change in the next build; the iPhone and Mac screens in sections 3 to 6 do not.

Conflicts with Apple's guidance

  1. Copy instead of Use on Mac. macOS gives providers no call to insert one value (completeRequestWithTextToInsert is iOS 18 and later only, checked in the 27.2 SDK headers). Trade-off: the person pastes, and the clipboard holds the value for 60 seconds.
  2. A confirmation that is also the item screen. Apple's alerts have a default and a cancel button. Trade-off in decision 7.
  3. Psss’s own sheet instead of a system alert for other-site and http confirmations. Trade-off: a custom component to keep, in exchange for a safe default on every platform.

Open questions

  1. Can a password list request insert one value, and how does a person reach “Choose Text to Insert”? The SDK header says prepareInterfaceForUserChoosingTextToInsert serves a separate text-insertion request on iOS 18 and later, and does not say whether completeRequest(withTextToInsert:) may be called from the password list. If it may not, frames 8 and 9 on iPhone use Copy as on Mac and the entrance is only frame 12. Device only (K12).
  2. After a fill from another site, offer “Also offer this login on heron-bank.example”? It would save the person the next search. It edits the item from a screen that has no edit mode, and it ties the login to a site they had to be sure of. Recommended: not in this change; the person edits the site in the app, and the search is the bridge.
  3. Should search include cards and notes? Cards would need the payment-form work first (autofill.md, the roadmap item on checkout frames). A note has no field to use. Recommended: logins and custom items only.
  4. Should “No logins are saved for this site” offer to add one? Today the only exit is Find Another Item… or Cancel. A person who has no login yet gets a dead end. Saving happens on sign-up (password generator), not here.
  5. Should the list show what the person last used first? With several logins for one site (frame 5) the order is the vault’s. A recent-use order exists elsewhere (Recently used).
  6. When Face ID fails or is cancelled, is silence enough (F11)? The system sheet closes and the page is unchanged, so the person may not know whether anything happened. Apple’s own flow behaves the same.
