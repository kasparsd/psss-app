The conflict alert and the lock notice

These two are already in the code and have not been seen by the owner in one place. They are drawn as the code has them, with the exact strings from App/Features/VaultView.swift and App/Features/VaultFileViews.swift. The alert is shown over the editor, which is where a refused save normally happens. Nothing is redesigned on this page. Wording I would change is listed at the end, separately.

When they appear.
  • The alert appears when a change (a save, a delete, a restore, an import write) is refused because the vault file was changed by another app or device after Psss last read it. The refused change is kept in memory while the alert is up.
  • Reload Vault reads the file again and drops the refused change. If the saved Face ID or Touch ID key no longer opens the changed file, Psss locks and shows the notice below.
  • Save My Change Anyway repeats the change over the file without the check and keeps the replaced file as one of the backup copies on this device. Cancel leaves things as the file has them; the form stays open.

Conflicts with Apple's guidance

  1. Three buttons and a long message in an alert.
    The HIG prefers two buttons, a short title and a message of one or two lines, and warns against a long message. The alert has to choose between a lossy action, a destructive action and a dismissal, and a message that explains both. A sheet with two explained choices would match the guidance better, at the cost of a new screen; this is the reason for the rewording above rather than a redesign.
  2. A destructive button that is not the cancel button, in the middle.
    The HIG puts the destructive role where it is easy to tell apart and never as the default. The code does that. Order on iOS (Reload Vault first) puts the safer action first, which is right.
  3. The lock notice in red.
    Apple's own lock and sign-in screens use red for failures, so the code follows the platform, but the project reserves red for deletion; see the table.
