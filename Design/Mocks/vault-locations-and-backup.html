Where a vault is kept, backup copies and self-hosting

Drawn on 23 Nov 2026 for the vault format in docs/format.md (section “What a person sees”). Nothing here is built. Inside the frames a person sees a vault and the places it is kept; the technical words are explained in this page's prose and in the decisions at the end. All data is fictional.

The owner's questions, and where each is answered.
  • Do people know where the vault is in their iCloud? Yes, if they look: create and devices, frames 3 and 4 say it is Psss's own space in their iCloud, not in the Files app, and listed as Psss in the iCloud storage settings. This page shows it again as the iCloud row under Kept in.
  • How can they back up? Section 5: Save a Backup Copy writes one encrypted file. A second location is not a backup, and the screen where a location is added says so (frame 3).
  • Can they have several instances? Several vaults (section 7), one vault in several locations (sections 1 to 4) and one vault on any number of devices (frame 1 and the device pages).
  • Can a regular iCloud Drive folder or file be used? A folder, yes (section 3): Psss makes Personal.psss inside it. A single file cannot be a place the vault lives, and frame 5 says why. A single file is what Save a Backup Copy and Export as KeePass File write.
  • How can people self-host? Section 4, in three steps of effort that are described under the frames, not in them.
  • Who holds the key, and what if it is lost? The person. Every place Psss keeps the vault holds only unreadable data. A backup opens with the recovery kit or the vault password; Psss cannot open it for anyone.
  • How do they leave? Export as KeePass File and Save a Backup Copy are always there. Removing a location never deletes what is already in it, and the vault stays on the device.

1. The vault's details, and adding a location

A vault has one or more locations, and each holds the whole vault. This device is always one of them. The details are reached from Setup, not from the main list, because most people never need them.

iPad: follows the Mac layout in a wide window, as a sheet or a split view with the vault list at the left, and the iPhone layout in a narrow one. Add a Location… on iPad opens a popover on the button, with the same three rows. The folder picker is the system one on every platform.

3. A folder as a location

A folder is the one way to use iCloud Drive, a disk or a network drive. Psss creates Personal.psss inside the folder the person picks. Many small files inside it are written by one device each, so no file is ever written by two devices. A single file is never offered, because one file that several devices rewrite is the problem the new format removes. A single file is what Save a Backup Copy writes.

iPad: uses the iPhone frames in a narrow window and the Mac frames in a wide one. The folder picker on iPad is the same system picker as on iPhone, in a popover when the window is wide. Files shows Personal.psss in the same way.

4. A server as a location

The address is one field. Psss tries it as WebDAV, then as the small Psss endpoint (detecting the type is a question in the decisions list). S3-compatible buckets, which need a bucket name and two keys, would sit behind one more link, not drawn here.

Self-hosting, in three steps of effort. None of this appears in the screens above. The screens only ask for an address and a login. Psss never hosts any of it, and all three hold only unreadable data.
  1. No server at all. A folder on a home server or a disk, kept in step by whatever the person already uses: Syncthing, Nextcloud, a NAS or a network share. They add it as A Folder (section 3). Psss needs nothing installed.
  2. Standard storage. A WebDAV address or an S3-compatible bucket. Most home servers, Nextcloud and many hosted storage services already offer one. They add it as A Server.
  3. The Psss endpoint. Three operations (list what is new, get a piece, put a piece if it is not there). Anyone can run it from the published specification and the reference server, on a small machine. Neither the specification nor the reference server exists yet, and the address in frame 11 is a placeholder.

iPad: uses the same fields. The password field uses the system secure text field, and the iPad keyboard's password suggestions are switched off, as on the other password fields in Psss.

5. Backup copy and restore

A backup copy is one encrypted file, a snapshot, that holds the whole vault and earlier versions. It opens with the recovery kit or the vault password. Restoring merges: it only adds, because combining two sets of changes can only add. Restoring into the vault it came from therefore never overwrites, and Open as a Separate Vault is the way to look without touching anything.

iPad: uses the iPhone layout in a narrow window and the Mac layout in a wide one. Save Backup Copy… and Open a Backup… use the iPad document picker. In a wide window the save panel is a popover.

6. Export as a KeePass file

The way out to other apps. It is a snapshot and a copy, never a place the vault lives.

iPad: follows the iPhone and Mac layouts by window width. Export on iPad uses the system document picker for the destination.

7. Several vaults

Each vault has its own locations. Personal might be in iCloud and a folder; a vault for work might be on this device only. Family is shared, see family sharing.

iPad: follows the Mac layout in a wide window, where the vault names are section headers in the sidebar, and the iPhone layout in a narrow one, where Setup lists them.

8. Syncing with no conflict prompt

The conflict alert of the earlier mock does not exist in the new format. Two devices that edit offline do not produce two versions of a file; each edit is a small piece of its own, and the item is worked out from all the pieces. Different fields both apply. For the same field the later change is current and the other is kept in the item's history. An edit made to an item that another device moved to Recently Deleted keeps the item and shows it; nothing is deleted outright.

iPad: shows the same screens, in the detail pane on a wide window and pushed from the list on a narrow one. There is no alert on iPad either.

9. Errors and edge states

A location that cannot be reached never blocks the vault, because the vault is always on the device. The screens say what is safe, then what to do.

iPad: uses the same pages. Remove This Location… opens an action sheet anchored to the button on iPad, and the alert on Mac keeps its centered form in a wide window.

Decisions for the owner

  1. Locations belong to a device, not to the vault. The list is headed Kept in and starts with this device.
    Rejected: A single list of locations that every device shares and follows.
    Why: A folder path, a disk and a server password mean something only on one device, and iCloud is account-wide. So a Mac can keep Personal in a home-server folder while the iPhone uses iCloud only; the Mac then joins the two. The cost is that two devices can show different lists. This is stated in the caption of frame 1 and must be confirmed against the format (see the first question below).
  2. Add a Location is in the vault's details, under Setup, not on the main path and not in onboarding.
    Rejected: A location step on first run; a Locations entry in the main list.
    Why: The simplicity budget (fewer than ten settings, no file-format vocabulary on the main path) and the 23 Nov rule that nothing asks the person to choose where something is stored. iCloud covers the person this is for. Pushback on the brief: a row labeled Add a Location… is itself a choice about storage, so I would hide the whole Kept in and Devices block until the person opens the vault's details, which is what frame 1 does.
  3. The words are “Kept in”, “location”, “backup copy” and “KeePass file”. Buttons: Add a Location…, Save a Backup Copy…, Export as KeePass File….
    Rejected: “Storage”, “destination”, “source”, “sync target”; “Archive”, “Snapshot” for a backup; “Export” alone for a backup (it is the KeePass word and would hide the difference).
    Why: “Location” is short and general enough to cover iCloud, a folder and a server. “Backup copy” is something a person can picture. The three actions are three different promises, so they have three different names. “Location” is the one word I am least sure of; it can be changed in one place.
  4. A second location is shown as a live copy, never as a backup, in the sentence where it is added, and in frame 1.
    Rejected: Calling a second location a backup; a “Backup” section that lists locations.
    Why: A second location follows every change, deletions included. If it were called a backup, a person who deletes something and finds it gone in both would feel cheated. The truth is also the safer design.
  5. A single file is never a location. The folder is named Personal.psss and holds many small files.
    Rejected: Offering Add a File; a single-file vault in iCloud Drive; a hidden folder.
    Why: A single file written by several devices is the problem this format removes; the explanation is one sentence on the folder screen. A visible folder is one a person can move, copy and back up with Time Machine. The cost is that the folder contains hundreds of files that look alarming if someone opens it.
  6. Question: Can Personal.psss show as one item in Files and Finder (a package or bundle) and still sync as a folder in iCloud Drive?
    Drawn as: A plain folder. The frames say “Folder” and give a file count.
    To verify: on a Mac and an iPhone. A package would stop people browsing the contents, which is good, and would show as one item with one size. Whether iCloud Drive syncs a package safely as a folder, and whether Files treats it the same way, is open (docs/format.md records the same question).
  7. Question: Is a location per device in the format, or is the vault's list of locations shared between devices?
    Drawn as: Per device, as in decision 1.
    To verify: with the format's author. The document says a client connected to two places joins them, which reads as per device. If the list were shared, a folder path would have to be stored in the vault.
  8. Question: Can an iCloud Drive folder be used reliably as a location?
    Drawn as: The picker lists iCloud Drive, and nothing warns about it.
    To verify: whether iCloud Drive can evict files that Psss has not opened recently (Optimize Mac Storage, or files not downloaded on iPhone), which would make the location look behind or partly missing. Also: a folder in iCloud Drive and the iCloud location are the same Apple Account twice, so it is useful mainly to share a vault with someone who is not on this Apple Account. Consider a hint in the picker's intro: “Already in iCloud? You do not need this.”
  9. A server has one Address field. Psss detects whether it is WebDAV or the Psss endpoint; an S3 bucket sits behind a link.
    Rejected: A first screen that asks the type; separate fields for every kind.
    Why: A newcomer does not know WebDAV from S3. People who run their own server know their address. If detection fails, the error says the address is not usable storage, not “wrong type”.
  10. Question: Can Psss detect the type of server from the address alone, and can Test Connection prove it can write?
    Drawn as: Test Connection means “can read and write at this address”.
    To verify: a WebDAV test (listing, writing a small test piece and removing it) and a Psss-endpoint test. Writing a test piece to someone's storage is a side effect and should be named in the screen.
  11. Add Server exists only after Test Connection has passed.
    Rejected: Adding the server first and showing errors later; a Test button beside an always-available Add.
    Why: A server that does not work should never become a row that says Up to date. The cost is that one button changes its label.
  12. Backup copies are manual. Psss does not make scheduled backups.
    Rejected: Automatic daily or weekly backup files to a folder.
    Why: The vault is already on every device and in every location; a scheduled file is a third copy that has to be put somewhere. A manual backup is what people expect after being told a second location is not one. I would add a reminder after a long time without a backup, if owners ask for it. Risk: many people will never make one.
  13. The backup file opens with the recovery kit or the vault password, and nothing else.
    Rejected: A separate password for each backup; opening it with Face ID.
    Why: One less secret to keep. The file is the point-in-time version of the vault, so it takes the vault's own ways in. Psss cannot open it for anyone.
  14. Question: What is the backup file called and what is its extension?
    Drawn as: Personal Backup 2026-11-23.psssbackup.
    To verify: with the owner. It must be unlike the .psss folder, and an extension that the system can associate with Psss for Open a Backup….
  15. Restore has two choices, Add to Personal and Open as a Separate Vault. There is no “replace Personal with this backup”.
    Rejected: A third choice that rewinds the vault to the backup; restoring into a new vault only.
    Why: Merging only adds, so replacing would need deleting what the vault has, which breaks the nothing-is-deleted-outright rule and cannot be done on other devices that already have the newer changes. Pushback on the brief: a person who restores to undo a mistake will expect a rewind. The answer is item history and Recently Deleted. One consequence is stated on the screen: an item deleted for good since the backup comes back.
  16. Export as KeePass File asks for its own file password and says what does not travel.
    Rejected: Reusing the vault password; an unencrypted export.
    Why: A vault that opens with Face ID may have no vault password. A file that reaches another app should have a password the person chose for it. A .kdbx file is always locked; there is no unencrypted option.
  17. Question: What does a KeePass export carry of history, previous passwords and Recently Deleted?
    Drawn as: Frame 31 says only that members, devices and sync do not travel.
    To verify: against the mapping in docs/items.md. Whether previous passwords become KeePass history entries and whether Recently Deleted becomes the Recycle Bin must be known before the screen promises anything.
  18. Removing a location never deletes what is in it. There is no “Remove and Delete”.
    Rejected: A second destructive button that deletes the copy at the location.
    Why: Nothing is deleted outright. Deleting the copy in iCloud or on a server also affects any other device or person that uses it. The person can delete the folder or the iCloud space themselves.
  19. Question: How does a person delete the iCloud copy when they want it gone?
    Drawn as: Frame 45 says the copy is not deleted.
    To verify: whether the iCloud settings let a person delete Psss's data, and whether a vault shared with other people can be removed by one of them. Until known, the screen cannot say how.
  20. Question: Can a lost device be removed from Devices that have Personal?
    Drawn as: The list shows devices with Last seen and no way to remove one.
    To verify: whether the format has a device removal that rotates what the device could read going forward. A person who loses a phone will look for this first. Without it, Face ID and the passcode on the lost phone are the only protection.
  21. The words Up to date and Behind each have one meaning, and Behind says what Psss cannot know.
    Rejected: Showing a green tick; a time-based “Not synced in 2 days”.
    Why: Storage can withhold recent changes, and Psss can only notice when other locations have changes this one lacks. “Up to date” therefore means “nothing Psss knows of is missing”. The honest copy is in frame 43.
  22. There is no alert when two devices edit at once. A quiet note appears only on an item whose password was changed on both, and History lists every change.
    Rejected: A banner for every merge; a “Choose a version” screen; the old conflict alert.
    Why: Nothing is lost, so nothing needs to be chosen. The one case with real consequences is the password: only one of the two is the one the website accepted. The note says so in a line. This supersedes the conflict alert; its lock notice still stands.

Conflicts with Apple's guidance

  1. Several full-width pinned buttons on a form sheet (Show in Files after Done).
    The HIG puts sheet actions in the navigation bar and prefers one primary action. Accepted on the 23 Nov mocks; kept for consistency.
  2. A list of locations with a status line in each row, and a blue labeled “Add a Location…” row.
    Apple's Settings lists put an Add row last, which this does. The status line under each row is body size in secondary colour, not a caption, as the two-size rule demands. The cost is less separation between name and status.
  3. A custom screen before the system folder picker.
    The HIG says to present the system picker directly. The intro is there because the person must learn that a folder, not a file, is chosen, and that Psss creates Personal.psss. The cost is one extra tap.
  4. The server password is entered on one screen with Test Connection, and the primary button changes its label to Add Server.
    A control that changes its label can confuse; the alternative is two screens. Apple's own account setup does the same (Next becomes Done).
  5. The folder-unreachable page uses a red full button for removal in the same stack as Reconnect.
    Apple uses a destructive row at the bottom of a list, not a button. Kept as a button because the project asks for labeled, visible actions.
  6. Mac details as a sheet with Done, not in the app's Settings window.
    The HIG says app-wide settings go in the Settings window. These are the vault's, not the app's, and a sheet from the vault list keeps the choice next to what it affects.
  7. An action sheet on iPhone and an alert on Mac for removing a location.
    This follows the HIG for each platform and matches the approved Recently Deleted mock.
