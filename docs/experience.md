# User flows and interaction design

The [HTML prototype](../prototype/index.html) uses fictional accounts and simulated browser fields. Each scenario is selectable from the prototype header. Changes last for the current page session.

| Flow | Steps | Recovery |
| --- | --- | --- |
| Fill | Focus sign-in → see site and matching accounts → choose → fill. | Unlock in place and return to the same account list. With no match, offer another account or a new login. Unknown or unsafe origins require a deliberate decision. |
| Create on a site | In signup, generate and fill a password → submit → review site, account and vault → save. | Keep the pending draft through a retry or vault unlock. Allow dismissal. Report a failed write and preserve the draft. |
| Update on a site | After submitting a changed password, choose the matching item → confirm update → retain old password in history. | Offer save as new if none of the matches is correct. Leave existing items intact until confirmation and a successful write. |
| Add in the app | New item → choose Login, Card, Note or Custom item → enter the relevant fields → choose vault → save. | Keep field values on validation errors. Allow explicit cancellation. |
| Fill at checkout | Choose a card by name and last four digits → fill cardholder, number and expiry → review the form. | For unmatched or unsafe fields, use explicit single-field insertion where supported. Enter the security code separately. |
| Retrieve a note or custom field | Search by title or tag → open the item → reveal protected fields on request. | Keep sensitive values out of list previews. |
| Open Strongbox vault | Choose file → provide password and key file if needed → unlock → check entries → enable AutoFill. | Explain unsupported variants, wrong key or unavailability and keep the source safe. |
| Import 1Password | Choose export → review counts, duplicates and unsupported items → choose vault → import → enable AutoFill. | Cancel before writing. Change duplicate choices or retry after failure. |
| Start empty | Name vault → choose local or iCloud Drive → set vault password → add first item or enable AutoFill. | Offer local storage when iCloud is unavailable. |
| Enable AutoFill | See provider setup → open system settings → enable Psss → test on a demo login. | Show verified browser support and installation steps for any extension needed. |
| Offline or conflicting changes | Read the last available encrypted revision → stage an encrypted revision for sync → surface edits requiring review. | Keep both revisions recoverable while the user resolves conflicts. |

## Screens and goals

Review of 2026-11-22. The native shell is a vault browser: sidebar of categories, list, detail. That is the surface people see least. Most of the product's life happens in the system fill sheet and the save prompt, so those come first, and the vault browser is a search box with a detail pane. Each row states the one job, the bar for “easy” (measured in taps, seconds or words, and checked on TestFlight builds) and the radical change from the current design.

## Key custody: the largest design bet

A vault password is the main source of first-run friction and of support burden. The proposal: generate a vault key as a short recovery phrase, store the derived key in the Keychain behind Face ID or Touch ID, and let the person set their own password instead if they prefer. The KDBX file still opens in KeePassXC or Strongbox with the phrase. This also fits the extension design that keeps Argon2 out of the AutoFill process.

Trade-off to decide in the security spike S6: a Keychain item that syncs through iCloud Keychain makes Apple account security part of the vault's security. A device-only Keychain item avoids that but each new device needs the phrase. The default has to be chosen with the threat model, not with the interface alone. Until S6 completes, a custom vault password remains the safe fallback.

## Cross-cutting rules

- Every screen has one primary action and no more than two secondary actions.
- Important actions are visible, labeled and prominent, never icon-only and never behind a menu or a hidden gesture. The primary action is a filled button with a text label. Secondary actions are bordered or plain buttons with text. Icons may accompany a label and never replace it for an action people need often. Tap-to-copy rows also show a “Copy” label.
- No “⋯” overflow menus (owner, 2026-11-23). A symbol with no words doesn't say what's inside, so nobody knows to click it. Every action is a labelled button where it applies. Rare actions on an item live inside Edit (“Move to Recently Deleted” at the bottom of the editor), and on Mac the menu bar repeats them with shortcuts. A menu is allowed only behind a button whose label names the choice, such as “+ Add” for the item type or the vault name on the unlock screen.
- Progressive disclosure applies to detail, not to the main job. Hide what is rarely needed or risky (protected values, type choice after tapping New item, advanced options) behind one clearly named control such as “Show” or “Customize”. Never hide the action a screen exists for.
- Where the platform default is icon-only, as in macOS toolbars and iOS navigation bars, add the title with `labelStyle(.titleAndIcon)` or move the action into the content. This departs from Apple's compact toolbar convention. The tradeoff is less toolbar economy for discoverability, and it is a design choice, not a requirement.
- Nothing asks the person to choose where something is stored.
- A secret is never visible without a deliberate gesture and never appears in a list preview, accessibility value or screenshot of the app switcher.
- Nothing is deleted outright (decided 2026-11-23, as in Photos). Every delete is a move to Recently Deleted with a 10-second Undo and no confirmation. Only the labeled “Delete Now…” and “Delete All…” in Recently Deleted remove for good, and they always confirm once; so does “Clear Previous Passwords”. A restore that is its own undo (a previous password) needs no confirmation. See [approved mocks](#approved-mocks-2026-11-23).
- The standard platform idiom wins. On iPhone, search-first is a recommendation that departs from Apple's sidebar and tab guidance for apps with deep hierarchies. It fits here because the hierarchy is shallow, but it is a design choice and not a requirement. Mac and iPad keep the split view.

## Review of the iPhone build, 2026-11-22

Captured on an iPhone 17 simulator (iOS 26.5, built with a temporary 26.0 floor). Evidence: [states](checkpoints/2026-11-22-iphone-review/states.png), [rows before and after](checkpoints/2026-11-22-iphone-review/rows-before-after.png), [pills before the row change](checkpoints/2026-11-22-iphone-review/before-pills.png).

### What works

- Typing starts on launch and results narrow with the first character. The floating search sits within thumb reach and content scrolls under it legibly.
- Pills filter in one tap, the selected pill is unmistakable, and All is the default (owner, 2026-11-24: Recent and Most used are a sort now, see “Sort”).
- The labeled “New item” button beside search is always visible, and its menu opens upward so the most common choice, Login, lands nearest the thumb.
- Detail shows a legible code with a countdown ring and gives every field a visible “Copy” (no separate Copy password button at the top: owner, 2026-11-23). The “Copied” confirmation is immediate. “Show” reveals a card number grouped by four.
- Adding from a failed search pre-fills the title and focuses it.

### What was wrong, and is fixed

- Returning from an item refocused search, which collapsed the navigation bar and hid “New item”. Focus now happens only on launch.
- Account emails rendered as blue links. “New item” and the setup gear were icon-only. The countdown rendered as a spinner. The title appeared twice on detail. “Copy card number” wrapped and made the page jump when it changed to “Copied”. The new-item editor did not focus its first field, so typed text went nowhere.
- A failed search showed a dead end. It now offers “Add “text” as a login”.

### What could be better, in priority order

1. **No real data behind the lock.** The app and the extension now unlock with Face ID, Touch ID or the passcode (see [autofill](autofill.md#unlock-prototype)), but the vault is still the unencrypted sample. The first-launch screens do not exist yet.
2. **Density.** Two-line rows gave about eight items per screen. One-line rows with tighter insets give about fifteen, nearly double.
3. **Repeated titles dominate All.** Seven “Acorn Fitness” logins in a row hide the rest of the alphabet. Group entries by site with a count and expand on tap, or sort recently used first within All.
4. **Pills overflow.** Cards, Notes and Custom are off screen at launch and nothing hints they scroll. Consider a trailing fade, or hide empty types.
5. **The Vault root screen is a leftover.** The iPhone Back button leads to a sidebar that duplicates the pills and has no purpose on a phone. Remove it on compact width and put Setup in a visible control on the list.
6. **Copy gives no feedback outside the page.** On iPhone the system shows a paste banner later, but nothing here says the copy will expire. Add “Copied. Clears in 60 s” once.
7. **Editor is a plain form.** No generator on the password field, no paste detection, no Save feedback. Screens 8 to 10 in the table are still open.
8. **Detail hides the rest.** Notes, attachments and history have no place yet. Add them under a clearly named “More” section, not a menu.
9. **Only dark mode was checked.** Verify light mode, largest Dynamic Type (the row switches to two lines), iPad and Mac.

### One-line rows and site icons

Decision: each row is one line, [icon] name … login, with the icon at 30 pt.

- Superseded by the shared row (“One row for All, Codes and Cards” under Places): the name is always over the account. A long email truncates in the middle, which keeps the domain visible.
- The name is not hard-capped at a character count. A width-based cap adapts to Dynamic Type and to wider iPad and Mac columns, where a fixed count would waste space or still truncate.
- Today the icon is a monogram tile whose colour derives from the site, so it is stable and works offline. Non-login items use their type symbol on grey. This is the slot for a site icon.
- Site icons are worth having and carry a privacy cost. Fetching a favicon tells a third party, or the site, that the person has an account there, and that contradicts “nothing leaves the device”. Rules:
  - Off by default. Offer once, in plain words, and keep it as one setting.
  - Fetch directly from the site over HTTPS. Never through a third-party icon service.
  - Cache the image in the vault as a KeePass custom icon, so it syncs, works offline and is never fetched twice. KeePassXC and Strongbox read custom icons, so the file stays portable.
  - Fall back to the monogram when there is no icon, and verify contrast of the letter on every tint.
- Risk to test: icons make many near-identical logos, so the login becomes the real identifier. The one-line layout keeps it on screen.

## Decisions

- Keep autofill on the system surface or browser form and use the app for viewing and editing the vault.
- On Mac and regular-width iPad, give categories, results and item details their own columns. On iPhone, open the searchable All list and put category navigation one native Back action away. Categories are scopes in the same vault workflow, so they share a navigation stack.
- Most people have one vault. Create it silently and show vault choice only when more than one exists. Say “vault” in the UI and show “KeePass (.kdbx)” only when choosing or exporting a file.
- Do not show “KeePass entry” as an item type. Use “Custom item”.
- The HTML prototype is frozen. Validate the remaining flows on native TestFlight builds, where the real AutoFill surface exists.
- Fill on explicit selection and leave form submission to the user.

## Mocks before building

A new or unclear screen is drawn and approved before any code is written. The mocks live in `Design/Mocks/`, one HTML page per feature, with `index.html` listing them. The owner approved this format on 2026-11-23; keep to it for the next ones.

How a mock page is made:

- **Start from the person, not the layout.** Before drawing, answer the `ui-clarity` questions: what is being created or changed, where it lives, who holds the key, how to get out and what happens next. The answers become the captions.
- **Every state, side by side.** Normal, empty, in progress, done and each error are separate frames on one page, so a missing state is visible as a gap. A flow reads left to right.
- **iPhone and Mac together.** Each state is drawn for both, so a difference between platforms is a choice someone can see. iPad is described in words under each section, since it follows the Mac layout when wide and the iPhone layout when narrow.
- **A caption under every frame** saying what the person sees and what they can do next. If the caption is hard to write, the screen is unclear.
- **Decisions at the end of the page.** Each one states the choice, what was rejected and why. This is where the reasoning is kept, so a later change argues with the reason and not with the picture.
- **Departures from Apple's guidance are listed separately,** each with the trade-off, as [AGENTS.md](../AGENTS.md) asks.
- **Existing screens are drawn as the code has them.** When a mock covers something already built, the strings come from the source, and wording that should change is listed in a table beside it. This is how the conflict alert and the lock notice were first seen as a whole.

Why plain HTML:

- One self-contained file per page, with no build step, scripts or images. It opens from the repository, shows in a diff and can be sent as it is.
- System fonts and `color-scheme: light dark`, so light and dark are both checked by switching the system setting.
- The project rules are built into the stylesheet: a device frame has two text sizes only (a title and a body variable), blue stands in for the system accent, red appears only for deletion and every action has a text label. A mock cannot quietly break a rule the app must keep.
- Controls are approximations of the native ones. A mock settles structure, wording, states and order. Spacing and exact control appearance are settled in the app, on a device.
- All data is fictional.

What approval means: the decisions list is what gets approved, not the pixels. Nothing in a mock is built, and no doc is changed to match it, until then. After approval the decisions move into the document for that concern ([items](items.md), [vaults](vaults.md), [migration](migration.md), this file), the screens are built, and an independent run checks them on a simulator against the mock's states.

Mocks are kept, and kept current (owner, 2026-11-24; before that a page was deleted once its feature was built and documented):

- **A mock page always shows the current decisions,** for as long as the screen exists in the app. When a decision changes, the page changes in the same piece of work: its frames, its captions, its clarity answers and its decisions list. A page is never left describing something that was replaced, and two pages never disagree.
- **One set of shared components draws every page** (`Design/Mocks/app/src/components` and `src/screens`), so a change to a row, a toolbar or an item page shows on every page at once. The components draw only the current design: no switches for older versions and no historic components are kept.
- **Each page ends with a “History” section,** a dated log in words only, newest first: what was tried or changed, what replaced it and why, and who decided. This is where earlier designs live once their drawings are gone, so nobody proposes them again without knowing why they were dropped. It needs no frames.
- **A page is removed only when its screen is removed from the app.** Its history then moves to the page that replaced it, or to this document.
- The older static pages in `Design/Mocks/*.html` that have not moved into the app follow the same rule when they are next touched.

## Native interface conventions

- Use `NavigationSplitView`, native lists and system search to browse and select vault items. On iPhone use the system’s compact navigation. Confirm the collapsed stack can return from details directly to results. Adapt regular-width iPad and Mac layouts to make effective use of the available space.
- Keep frequently used actions in the toolbar and give them clear labels and SF Symbols. Keep passive status in the title, section header or detail view. Respect the user’s accent color and use semantic styles for secondary text and destructive controls.
- Keep item semantics, wording and safety consistent across platforms. Use the appropriate platform idiom for each action, including keyboard shortcuts and commands on Mac and system sheets on iPhone.
- Preserve keyboard focus and list position unless the person’s action calls for navigation. Keep actions available to VoiceOver and avoid exposing masked content in accessibility values.
- Use the actual system AutoFill or browser surface for filling. The HTML test form and picker are a storyboard. The native build implements screens 6 and 7 from the table above: a search-first home and a copy-first item detail.
- Home: iPhone opens on the list, and Mac and iPad open with the sidebar visible. There is no pill row (owner, 2026-11-24: a Filter menu replaced it, see “Places: All, Codes, Cards”). The All list is narrowed by **Show** (All, Logins, Notes, Custom), **With** (Passkey, Notes) and ordered by **Sort**; Codes and Cards are places of their own. All is shown by default and its order is the Sort setting (“Recently used” unless the person chose another). Typing always searches the whole vault, whatever Show and With say. On iPhone, search is the iOS 26 search tab at the end of the tab bar, within thumb reach (see “Tab bar and Codes” below); the labeled Add button is in the top bar. The search tab lists the whole vault. On Mac, search is in the toolbar and Return opens the top result. The sidebar remains the standard navigation.
- Detail: the icon and the name lead the page, with no copy buttons under them (removed again 2026-11-23 at the owner’s request: the fields below hold all the data, each with its own Copy). Each field is also one row with a visible “Copy” label, and a click or tap copies it with a short “Copied” confirmation and a haptic on iOS. Passwords, card numbers and secure note bodies stay hidden until the labeled Show button is used, and accessibility reads them as hidden. Copies stay on the device, are marked concealed on Mac, and expire after 60 seconds. A login with a seed shows a live six-digit code with a countdown ring, verified against the RFC 6238 test vectors.
- The sample vault contains more than 300 logins, 10 cards, 20 notes and 30 custom items. Logins with a code each have their own seed; one makes an 8-digit code every 60 s and one has a seed that cannot make a code. Four cards are hand-made (with a security code, without one, and one expired) so Cards shows every state. Some logins carry a recent-use date.

### Places: All, Codes, Cards (approved 2026-11-23)

The sidebar is visible on iPad and Mac (the person can hide it) and lists All, Codes, Cards, Logins, Notes, Custom items and Recently Deleted, each with a count. It is the one control that chooses a place or a kind. **Filter menu replaces the pills (owner, 2026-11-24).** Three separate choices combine for the All list: **Show** (exactly one kind: All, Logins, Notes, Custom), **With** (any number; an item must have all that are ticked: Passkey, Notes) and **Sort by** (exactly one, see “Sort and row lines”). ### Field row convention (owner, 2026-11-23)

- **The whole row copies (owner, 2026-11-24).** On item pages a tap or click anywhere on a row that has a copy icon copies it; the icon stays as the visible cue and the eye never copies. Rows without a copy icon do nothing. The code row copies the current code. iOS shows a pressed state and Mac a hover highlight; VoiceOver sees only the labeled icon buttons (the row layer is hidden from it). `FieldRow`, `copiesOnTap` and `CopyRowStyle` in `App/Features/FieldRows.swift`.
- A field's action sits at the trailing end of its own row, on the same line as the value or input: copy icons on item pages, info buttons in rows, and editor actions such as “Add code” / “Replace code” beside the setup key field. Destructive actions (“Remove code”) get their own row below.
- Every trailing icon or button is right-aligned with the same inset from the row's trailing edge as the text has from its leading edge, on iPhone, iPad and Mac. Built so: the copy icon's glyph sits flush with the trailing text inset and its touch target grows to the left of it; list rows on Mac use equal leading and trailing insets (4 pt); the code and Copy buttons of Codes end on the same inset. Info buttons only ever sit inline after the text they explain.
- Copy on item pages is the copy icon (`Design/Mocks/copy-icons.html`, approved 2026-11-23), with an accessibility label naming the field, a tooltip on Mac and a 44 pt target. Copying turns it into a checkmark (system replace animation, light haptic) and shows a pill near the bottom naming what was copied (“Password copied”) for about two seconds; Reduce Motion cross-fades. Codes keeps its in-row “Copied”. Superseded by the next rule (owner, 2026-11-24): the row copies too. ## Lock policy: follow Apple Passwords (2026-11-22)

Apple Passwords always asks for Face ID, Touch ID or the device password to open, offers no switch to turn that off, locks when the device or Mac locks or sleeps, and on Mac also after about a minute of inactivity. Psss follows that: authentication is not opt-in and not a setting. The only setting is how long the app may stay in the background (Immediately, 1, 5 or 15 minutes), because people hold different views on that and it never weakens the floor. Mac already locks on sleep, a sleeping display and a locked screen; inactivity locking is on the roadmap.

## Button and action audit (2026-11-22)

**Destructive styling.** Keep `role: .destructive`. SwiftUI renders it in system red, which is the platform behavior ([Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons), [ButtonRole.destructive](https://developer.apple.com/documentation/swiftui/buttonrole/destructive)). Apple's own destructive form rows and dialogs use red text, so we add no custom red or tint.
Rules: destructive is never the prominent style, the row is text-only, a specific title names the action, and every destructive action confirms or can be undone ([Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts)).
This was checked against Apple's guidance, not by capturing Apple's apps side by side.

**Conventions after the audit.**

| Context | Style | Icon |
| --- | --- | --- |
| Primary action on a screen (Welcome, empty vault, Unlock, Fill, Save) | Prominent | Label only where it clarifies |
| Secondary choices beside it | Bordered | No |
| Toolbar | Labeled Text (Edit, Add), gear for Setup | Gear only |
| Setup form rows (Lock Now, Start Over…, Lock picker, placeholders) | Plain row | No icon |
| Destructive (Delete Now…, Delete All…, Clear Previous Passwords, Start Over…) | System red role, text-only. Never prominent. ### Setup and lock screen fixes (2026-11-23)

- **Setup vault details.** A plain line first (“A KeePass file, encrypted with your vault password.”, or “…with your vault password and a key file.” when a key file is part of the key, from a flag on the vault reference that is set at creation, password unlock and password change; nothing about the file itself is kept), then Name, Location, Modified and Items. - **Text sizes.** Vault list, detail, editor, lock and Setup screens use the title size and body only. The one stated exception is the verification code digits on the item detail, shown in a large monospaced size because they are content to read and copy, not chrome (the preview in the add-code sheet uses the title size). Secondary text uses the secondary colour; field names above values are body size in secondary colour.
- **Problems are not red.** Wrong-password errors, the “Face ID no longer opens…” explanation, mismatched passwords and key file errors on the lock screen and the create, open and change-password sheets use `ProblemText`: a warning symbol and the words in the primary colour (secondary when nothing went wrong, such as a password changed with leftover backups). - **Lock notice.** A cancelled Face ID prompt leaves the lock notice in place. It clears on success or when a new problem replaces it.
- **Removed item.** The alert reads “It was removed on another device or in another app, so the editor was closed. Changes you had not saved were not kept.”
- **Forgot password.** For a vault Psss created the footer reads “Forgetting removes this vault and its backup copies from this device. This cannot be undone.” With Face ID or Touch ID on, it adds “and turns off Face ID for it” (forgetting removes the file, its backups and the saved key).

## AutoFill reminder (approved 2026-11-23)

The owner approved [the mock](../Design/Mocks/autofill-setup.html) with one change, in his words: "for the initial onboarding, after creating the vault the user already gets the Face ID unlock request so it seems like placing the prompt inline (like no 6, option a) is the best approach. don't want to push too many decisions right away." There is no step or sheet after a vault is created. The card is how a new person learns about AutoFill, and it is the same on iPhone, iPad and Mac.

- **The card.** The first row of the vault list, so it scrolls away with the list and never covers a row. In a new empty vault it sits above the empty-state text. Shown only for a real, unlocked vault while AutoFill is off and the card is not snoozed by Later: never in the sample vault, never before a vault exists, never while searching or in a filter with nothing to list. Plain content: no alert, badge, notification or sound. Headline in body size and bold, then body text, one filled button and a plain “Later”.
- **Words** (iPhone and iPad say “iPhone” or “iPad”, Mac says “Mac” and “System Settings”):
  - First time off: “AutoFill is off”. “Psss keeps your logins. Your iPhone fills them in Safari and apps, and it needs your OK once. Until then, nothing fills.” Buttons “Turn On AutoFill” and “Later”.
  - After the system prompt was used and AutoFill is still off: “AutoFill is still off”. “Nothing fills yet. To turn it on yourself: open Settings, tap General, tap AutoFill & Passwords, then switch on Psss.” Buttons “Open AutoFill Settings…” and “Later”. On Mac: “open System Settings, choose General, choose AutoFill & Passwords, then switch on Psss”.
  - It was on and is off again: “AutoFill is off again”. “AutoFill was turned off in Settings, so Psss cannot fill logins right now.” Buttons “Turn On AutoFill” and “Later”.
  - It came on after it was off: “AutoFill is on”. “Open a website and tap the password field. Choose Psss from the suggestions.” (Mac: “Open Safari, go to a sign-in page and click the password field. Choose Psss from the menu.”) Button “Done”. It replaces the card once, in place, and is gone after Done or the next launch.
- **The button.** The first time, “Turn On AutoFill” asks through Apple's prompt (`ASSettingsHelper.requestToTurnOnCredentialProviderExtension`, iOS 18 and macOS 15, below this project's floor of 27). While Apple's prompt is up the card keeps its words and the button does not fire twice. A yes then shows the confirmation. A no, or no prompt at all (an unsigned Mac build), shows the steps in the card, and the button then reads “Open AutoFill Settings…” and opens the AutoFill page in Settings. The app never asks the system twice in one stretch of AutoFill being off, which also keeps the system's 10 second wait. When Settings cannot be opened, one alert says “Settings did not open” (“System Settings did not open” on Mac) with the steps in words and OK.
- **Later.** (Called Hide until 2026-11-23; renamed at the owner's request, and since the same day it snoozes instead of hiding for good. The approved mock draws “Hide” and the old permanent behaviour; its labels were changed to “Later” and a note says where it differs.) Removes the card at once and remembers the date on this device. The card returns once 7 days have passed (`AutoFillReminder.snoozeInterval`) and AutoFill is still off, with the same words it would have had, and Later snoozes it again. One line says so: “Psss will remind you in a week. AutoFill stays in Setup.” with OK, gone by itself after a few seconds. Why a week: long enough not to nag a person who is busy or still deciding, short enough that a switch which does nothing until it is on is not forgotten. The time is judged each time the card is drawn, so the card also returns while the app stays open. Seeing AutoFill on clears the snooze for good, so the card returns, as “off again”, if AutoFill is later turned off; the same moment lets the button ask the system once more. A clock set back before the snooze date does not keep the card hidden.
- **Empty vault.** The last line is “Sign in to a site in Safari and choose Save in Psss.” while the card shows or AutoFill is on. When AutoFill is off and the card is snoozed, the longer line that says to turn on Psss in Settings stays.
- **Setup.** The AutoFill section sits above Reset, so the destructive Start Over stays last (order: Vault, Security, AutoFill, Reset; same on iPhone, iPad and Mac). It is two groups. The first is the state as plain text, not a control: “AutoFill is on” with “Psss fills your logins in Safari and apps.”, “AutoFill is off” with “Psss cannot fill logins in Safari or apps yet.”, or “Psss cannot tell if AutoFill is on” with “Open Settings to check. Your vault is fine.”. The second is the action row, the card's button, with a footer: while off, “Your iPhone does the filling, and it needs your OK once. Psss cannot turn it on for you.” (after the prompt: the steps in words); while on, “Passwords and passkeys are switched in Settings, General, AutoFill & Passwords.”; when it cannot tell, “If this stays, Safari still shows whether Psss fills.” Setup shows this in the sample vault too, since it is about the device. There is no second button for verification codes: whether iOS has a separate switch for them is still an open question in the mock, so the footer does not claim one.
- **When it is read.** `ASCredentialIdentityStore.getState` at launch, after unlock and whenever the app becomes active (on Mac also when the application becomes active). When it finds AutoFill on after it was off, it sends the vault's identities to the system at once.
- **What the device remembers.** Local app preferences, per device, not in the vault file and not synced: the date Later was chosen, whether the system prompt was used, whether AutoFill was seen on, and whether the last reading was off. The decisions are in `AutoFillReminder` (App/Core) and are tested without a device; the views are in `AutoFillCard.swift`.
- **Not built.** The step after the Face ID question (section 1 of the mock, frames 1 to 5 as a step) was rejected by the owner and is not built. The unsigned Mac build shows the card forever and its prompt never appears; nothing in the app says “developer”.

### Recently Deleted and delete with Undo

- **Where.** The last row of the vault section in the Mac and iPad sidebar, and, on iPhone, the last entry of the Filter menu (owner, 2026-11-24; it was the last pill). Rejected: a Filters entry, a row in Setup, a search scope. The risk is that the pill is off screen at launch; the Undo capsule covers the first minutes and the empty state says where it lives.
- **Moving to Recently Deleted has no confirmation.** The editor row reads “Move to Recently Deleted” (default colour) with one line under it (“You can bring it back for 30 days.”), and a capsule with a labeled Undo follows for 10 seconds, plus Edit, Undo Move to Recently Deleted (⌘Z) on Mac and iPad. After Undo on Mac and iPad the item is selected again. Rejected: a red “Delete Item”, and keeping “Delete Item…” with a confirmation, and a modal Undo alert. Apple says not to confirm undoable actions.
- **Deleting for good always confirms**, for one item (“Delete Now…”) and for all (“Delete All…”, the count in the title and on the button). Rejected: no confirmation for one item, typing a word. Backup copies are named because rollback copies and iCloud's older versions may still hold the item.
- **Bulk button is “Delete All…”, not “Empty”** (a wording suggestion the owner accepted; easy to flip).
- **Read-only detail** with Show and Copy and no Edit; “To change this item, restore it first.” Restore is the one filled button, “Delete Now…” a plain red button.
- **A failed Restore reuses the conflict alert**, so one concept has one wording.
- **Rows say “Deleted 3 days ago · removed for good on 20 Dec”.** The absolute date is the one that matters; the relative one answers “was it me?”. This is the one exception to the absolute-dates rule in [items](items.md#created-and-edited-dates).
- **The sentence about other KeePass apps** (“Other KeePass apps show these items in their Recycle Bin and do not remove them.”) appears once, in the list footer and the empty state, not on rows, in Setup or in the confirmations.
- **As built.** iPhone: the Filter menu’s Recently Deleted entry (it was the last pill), “Delete All…” in the navigation bar (not Apple's trash symbol), confirmations as alerts (title naming what is deleted, “This can't be undone” style message, a red Delete button and Cancel; a confirmation dialog hangs from a toolbar button or from a view inside the navigation content, and iOS 26 then draws it as a popover with one red button and no Cancel, which an alert never does), swipe on a row offers Restore as a shortcut. iPad: the sidebar row (with a count) or the pill row by window width, confirmations as the same centred alert as on iPhone (a confirmation dialog is a popover with no Cancel there), the Undo capsule at the bottom of the detail column. Mac: sidebar row with a count, “Delete All…” in the toolbar in place of Add, Restore and “Delete Now…” in the content, right-click Restore, confirmations as alerts whose default button is Cancel, Edit, Undo Move to Recently Deleted (⌘Z). Rows read “Deleted today”, “Deleted yesterday” or “Deleted n days ago”, then “removed for good on” the date; with one item “Delete 1 Item Now”. The read-only detail uses the same field rows as the vault's own page (copy icon, eye, Copied pill; `FieldRow`), and lists fields in the vault's own order (username, password, expiry, website, notes), not the mock's website-first order. It does not show the verification code or passkey rows of a deleted login. After Restore the list shows with nothing selected; after Undo nothing opens. A refused Restore or Undo is the conflict alert, and a reload that shows the item gone drops the offer to save over it. Future Help text: where Recently Deleted is, that items wait 30 days, that Delete Now… cannot be undone and that other KeePass apps keep showing the Recycle Bin.

### Departures from Apple's guidance, accepted with the mocks

| Departure | Trade-off |
| --- | --- |
| Undo capsule on iOS | iOS has no standard toast; shake to undo and the Edit menu are not discoverable on iPhone. The labeled capsule is visible and tappable but is a custom component that disappears after 10 seconds. VoiceOver gets the announcement plus an Undo action. Shake to undo is not used |
| Recently Deleted as a Filter menu entry (once a pill) on iPhone, not a list row | Notes and Photos list it in a folder list. Psss iPhone has no folder list by design (search-first, already recorded), so the last pill is the closest fit |
| Delete Now… and Delete All… as labeled text buttons, not an icon-only trash | Apple's toolbars would use a trash symbol. The project rule is visible, labeled actions; the cost is space in the navigation bar |
| Confirmation as an alert on iPhone, iPad and Mac | Alerts always show Cancel; a dialog anchored in the navigation content became a popover without Cancel in iOS 26, on iPad too. Start over and Forget Vault use alerts as well |
| Section headers and footers at body size | The two-size rule; less separation from the row below, secondary colour does that job |
| Several buttons in one list row (Show, Copy, Restore) | The HIG discourages more than one control per row. These rows have no row action, buttons are at least 44 pt tall and wrap onto their own line on iPhone. An ellipsis menu would hide important actions |
| Destructive “Clear Previous Passwords” as a plain red row | Apple's grouped-form idiom; the confirmation does not repeat red as a filled button |
| Alert with three buttons and a long message (conflict) | The HIG prefers two buttons and a short message. The alert must choose between a lossy action, a destructive one and a dismissal; a sheet with two explained choices would match better at the cost of a new screen, so the wording is shortened instead |
| Warning glyph in system orange on the import sheet | The HIG allows semantic system colour; neither the accent nor the deletion red. If the owner wants no colour but the accent, keep the heading and border and drop the glyph colour |
| Full-width pinned action on an iOS sheet | The HIG puts sheet actions in the navigation bar. The mock keeps one labeled primary action at the bottom and Cancel at the left; it does not match system sheets such as Mail's |
| Import progress with no Cancel | The HIG says to let people cancel long operations. The write is one commit of a few seconds that cannot be interrupted safely |
| New detail rows with labeled buttons next to today's quiet copy glyph | The two idioms sit together until the owner decides whether to relabel today's rows |
