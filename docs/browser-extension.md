# Browser extension

Psss fills in Safari and native apps through the system AutoFill provider. Other browsers need their own route, so there is one shared WebExtension (a flat folder, `Extensions/Browser/src`), one native host for Chrome and Firefox, and a Safari app extension that bundles the same files with the Mac app. The Safari extension is part of the Mac app, not a separate download. iPhone and iPad have none (since 2026-11-24, see below). Chrome and Firefox remain a prototype outside 1.0 (see [roadmap](roadmap.md)).

## Does system AutoFill reach other browsers?

| Platform | Result | Consequence |
| --- | --- | --- |
| iPhone and iPad | Chrome, Firefox and Edge render with WebKit and use iOS AutoFill, so the credential provider is offered. Reliability varies by browser (Chrome puts its own manager first). Browser extensions do not exist outside Safari. | The system provider is the only route. Test each browser on a device and publish the grid. |
| Mac | The provider is called for Safari and native fields. Chrome and Firefox draw their own web content and are not expected to call it. Apple ships a separate Passwords extension for them, and third-party managers ship their own. | An extension and a native host are the only route. Confirm the negative result once with the provider enabled. |

## Safari: bundled with the app

The Safari extension that works today ships inside Psss-macOS only (target `SafariExtension-macOS`, embedded next to the credential provider). The general `SafariExtension-iOS` target was removed on 2026-11-24 (decision below). A new iPhone and iPad target of the same name, for cards and addresses only, is being built ([below](#iphone-and-ipad-cards-and-addresses)): Release builds of Psss-iOS do not embed it yet. Its web files are the shared `Extensions/Browser/src` folder with no overlay: the Safari manifest is the base manifest, which `build.py check` verifies. Its native half is `Extensions/Safari/SafariWebExtensionHandler.swift`, a relay client of the running Mac app (below, “Safari over the relay”): it answers the same protocol as the Chrome and Firefox host. The settings page is left out of the Safari bundle because Safari has no browser save prompt to switch off. The extension folder is flat because Xcode's synchronized folders flatten resources into the bundle.

The system AutoFill provider already does most of the work in Safari, so the extension adds a small, specific set of things:

| | App with system AutoFill alone | Added by the Safari extension |
| --- | --- | --- |
| Fill a saved login | Yes, on iPhone, iPad and Mac, through the keyboard suggestion or the picker, which lists all logins | The same fill from a toolbar popup and the ⌘⇧P shortcut on Mac. No new capability. |
| Passkeys and verification codes | Yes | Nothing yet: the popup fills logins only |
| Generate a password on a sign-up form | iPhone and iPad on iOS 26.2 or later (system "Use Strong Password"). **Not on Mac**: macOS has no API for it | **Mac: "Generate, Fill and Save"** fills the password and its confirmation |
| Save a new login or update a password | iPhone and iPad on iOS 26.2 or later. **Not on Mac** | **Mac: the generate button saves the login** (or updates the saved one for that account). There is no save-on-submit capture yet, so a typed password the person chose is not saved |
| Find a login for a site the auto-match missed | The picker lists all logins | A search field in the popup, with a warning before a login is filled into a site it was not saved for. Same result, second place to do it |
| Toolbar button, keyboard shortcut | None | Yes |
| Setup | Enable Psss under AutoFill & Passwords | Mac: also enable the extension in Safari Settings, Extensions, once, and allow it on sites. The app shows a card for it (below) |

In short: the prototype pairs generate and save on sign-up forms. The shared extension can also fill a checkout from a selected sample card through the prototype host. Connecting the real encrypted vault to the bundled Safari extension and external browser host remains open, as do save-on-submit and detection when a password is typed by hand.

### Why iPhone and iPad have no Safari extension (2026-11-24)

On iPhone and iPad the extension duplicated what system AutoFill already does (fill, Strong Password, save on iOS 26.2 and later, passkeys, codes), added a second setup step and a permission prompt asking to read every website, and its handler is the least protected code in the app (see [architecture](architecture.md)). It also showed up in Safari's Manage Extensions list, which Safari cannot hide for an embedded extension. The owner chose to remove it from the iOS builds for 1.0 and keep it on Mac, where it fills a real gap (macOS has no generate or save API).

**Critical, later: fill cards and identities in Safari on iPhone and iPad.** iOS has no third-party AutoFill for payment cards or addresses, so this is the one thing an iOS Safari extension could do that the system cannot, and the owner wants it (priority set 2026-11-24). It needs the iOS target back, a popup that lists cards and identities for the page, and the handler relaying to the unlocked app instead of answering `unsupported`. The app’s side of [the reminder](#the-reminder) is built and waits for it. Tracked on the [roadmap](roadmap.md) under M2. Mock: `Design/Mocks/app/src/pages/IosSafariFill.tsx` (`#/ios-safari-fill`), approved 2026-11-26 with two decisions. After the person unlocks in Psss the extension gets a short read permission of about two minutes, cleared when the app locks. One tap on Fill writes the card's name, number, expiry and a saved security code together; there is no separate Fill Security Code tap (owner's change to the earlier draft, which had a separate step). An address row reads full name · city.

## Design

One extension source in `Extensions/Browser/src`, three small manifest overlays in `Extensions/Browser/targets`, one build script. The extension is a toolbar popup and nothing else.

- **Kept between openings** (owner, 2026-11-26). The popup keeps the search text, the chosen search fields and a typed username for the same site and vault, in the browser's session storage (`src/kept.js`): in memory only, gone when the browser quits, cleared when the popup sees the vault locked. Passwords, cards and host replies are never stored, and a username read from the page is not kept, only one typed in the popup; it is dropped once saved, and a username on the page wins over it. Return does nothing on a search kept from an earlier opening until it is typed in or a search field is chosen, so it cannot fill a login searched for on another page of the site. A lock and unlock that happens while the popup is closed is not seen, so the search survives it.
- **Least privilege.** Permissions are `activeTab`, `scripting`, `nativeMessaging` and `storage` (session storage only, for the line above; browsers show no install warning for it), plus the optional `privacy` described below. There is no content script, no host permission and no background worker. Nothing runs on a page until the person opens the popup (or presses the command shortcut), which grants `activeTab` for that tab. The fill function is injected into the top frame only. `build.py check` fails if a permission, optional permission, host permission or content script is added without updating this document.
- **Origin.** The extension takes the URL from the browser's tab record, never from the page. It sends only an origin. HTTPS is required, with plain HTTP for localhost. URLs with embedded credentials are refused. The host enforces the same rule and rechecks the origin before it releases a secret, so a reference alone is useless. The popup revalidates the tab origin between listing and filling.
- **Secrets.** The login list carries titles and accounts only. The secret crosses the boundary once, on the person's click, as an argument to the injected function. It is never stored in extension storage, logged or echoed back.
- **Frames.** Cross-origin frames are not filled. Payment iframes and embedded sign-in frames are a separate decision (see [autofill](autofill.md#payment-cards-and-other-fields)).
- **No remote code.** Chrome Web Store MV3 policy requires all logic in the package. The check rejects `eval`, `Function`, inline scripts and remote script or import URLs.

**Field roles for fill.** The app, native AutoFill provider and browser host resolve fields using the same [canonical fill roles](items.md#canonical-fill-roles). The WebExtension parses [HTML autocomplete tokens](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#autofill) while keeping section and billing or shipping context. Tested aliases cover form labels and HTML names when an explicit field token is absent. For cards and addresses only (never sign-in), a field with no exact alias is also read word by word (2026-11-26): its name, id, label and placeholder are folded (accents removed, `ß` to `ss`), split at camelCase and punctuation, cut at `(` or `*`, with trailing hints such as “required” or “MM/YY” dropped, and the last words must form an alias while every word before them only adds context (billing, shipping, `ctl00`, `txt`…) or names the same role. So `billing_address_postcode` and “ZIP / Postal code” are found, and `gift_card_number`, `user_name` or `house_number` are not. A person's name takes only person context (billing, recipient, “your”…), so `street_name` is not a name; card, credit and payment are context for card fields only, so `card_company` is not the organization; ASP.NET's `ContentPlaceHolder1` is ignored. A card number whose hint says it is partial (“last 4 digits”, “masked”, a number outside 13–19) is not the card number, and a phone or `+`-prefixed box is never the country. Sources that disagree give no role, and a source of more than six words gives nothing. A field found this way counts as undeclared, so a field the page declares wins, and every visibility, form, block and number-kept check still applies. Aliases cover English, German, French, Spanish, Italian, Dutch, Polish, Portuguese and Latvian; other scripts (Cyrillic, Greek, CJK) are not read. A box called only “security code” in any of these languages must sit close to the card number. Options considered and set aside for now (a learned model in the page, or Mozilla's TinyBERT field classifier natively) and how they would be measured are recorded in the [roadmap](roadmap.md#later-in-priority-order). The injected matcher skips ambiguous inputs and rechecks the top-frame origin. Checkout fill requires an explicit card selection, is available for sample cards in the prototype host, and fills the cardholder, number and expiry. Security codes remain under manual copy in the app. Future model suggestions belong in the vault mapping review. Fill uses deterministic rules.

**Browser save prompt.** Chrome and Firefox offer to save the password in their own manager after a sign-in, which doubles Psss's job. The popup's Settings button opens a settings page with one labeled switch, "Turn off browser password prompts". Only then does the extension request the optional `privacy` permission, from that page rather than the popup because Chrome's permission dialog would close the popup mid-request, and set `privacy.services.passwordSavingEnabled` to `false`. "Turn browser password prompts back on" clears the setting and drops the permission. The browser reverts the setting by itself if Psss is disabled or removed. If another extension or a policy controls it, the page says so and disables the button. Saved passwords already in the browser are untouched, and the browser's autofill is not changed. Safari has no such API, so its manifest drops the permission (`null` in `targets/safari.json` removes a key) and the popup hides Settings and its footer. The store listing must justify `privacy` as "switch off the browser's own password prompt at the user's request".

**Search.** The popup lists the logins matched to the page and always offers a labeled search over all logins (`search { origin, query, fields? }`, metadata only, at most 20 results). Results are in two groups (2026-11-25, owner), as the app's list groups its rows: "For This Site" (the website matches the page) and "Other Matches" (matched by name or search but saved for another site or with no website), an empty group left out (`src/groups.js`, tested in `tests/groups.test.js`). An Other Matches row says where it is saved, "Saved for githosting.example" (the matched part in bold) or "No website", wrapping and never cut to one line. Fill is the same button on every row and asks nothing more: the heading and that line are the check against a lookalike site. A click on an Other Matches row sends `credential` with `manual: true`. The host releases a non-matching login only with that flag, never on plain HTTP or any origin the policy refuses, and the shipping app replaces the flag with its own approval prompt. Only extension UI can send it, so a page cannot trigger it.

The messages between extension and host are versioned and listed in `src/protocol.js`: `ping`, `candidates { origin, vault }`, `search { origin, query, fields?, vault }`, `credential { ref, origin, vault, manual? }`, `vaults`, `switch-vault { vault }`, `unlock-vault { vault }` and `save { origin, vault, account, secret }`. **Version 4 (2026-11-25)**: several vaults can be open at once, so every request that reads or writes logins names its `vault` (`candidates`, `search`, `credential`, `card-candidates`, `card`, `save`). The host answers from that vault when it is open, `locked` (or `not-available`) when it is not, and `not-found` for an unknown, missing or over-long id. It never reads another vault instead. `active` in `vaults` is only the vault the app shows, the popup's default. **Version 3 (2026-11-24)**: vaults carry a `state` instead of a `locked` flag, `unlock-vault` is new, `switch-vault` no longer unlocks, `save` names its vault and candidates carry the `website`. Version 2 added the field-aware search and the vault messages. A host or extension of another version answers `unsupported`.

### Popup style, search and vaults

Built 2026-11-24 from the approved mock (`#/browser-extension`).

- **Style.** The popup draws the app's list: a card of rows, each with a coloured letter tile (the brand icons are in the app, not in the extension), the name over one grey line, a passkey glyph when the login has one, and a visible capsule **Fill** (the same on every row; filled when exactly one login matches the page). System font, the system accent colour (`AccentColor`) and light and dark follow the browser's colour scheme. Two text sizes only. The header carries the logo mark (the hidden field, inline SVG in the text colour so it works in both schemes) left of the title; it does not repeat the page's site, which the address bar shows. The toolbar icons (`action-16/32.png`, also the manifest's `icons` 16 and 32) are the small mark A2, a ring with one dot and butter inside, rendered from the SVG (small cut at 16 px, large cut at 32); Chrome draws one image whatever the theme, so the filled mark needs no light and dark pair. Safari uses the same coloured icon (no template image: Safari shows coloured extension icons as given). The extensions page and store icons (`icon-48/128.png`) are the app icon tile. All four are generated by `scripts/build-extension-icons.mjs`; do not edit them by hand. See [brand](brand.md), "Small mark".
- **Search.** The field has the focus the moment the popup opens (checked in the Chrome and Firefox suites: `document.activeElement` is the field). Typing replaces the site list with results, A to Z, and shows the pills Name, Website and Username with a count each, dimmed (disabled, never hidden) at 0. A pill narrows the search to that field, as in the app. The host does the matching in Swift Core with the app's `ItemSearch` (`App/Core/ItemSearch.swift`, moved out of `RecentlyDeletedText.swift` so the host can compile it) and returns, per result, `found` (the field shown), `hit` (its text) and `hitRange` (UTF-16 start and length of the part to set in bold), plus `counts` for every field whatever is chosen and `total`. The page never receives the vault; counts and ranking come from the host.
- **Layout** (2026-11-24, changed 2026-11-25, from the mock `#/browser-extension`). Header: the logo alone (its accessible name is "Psss"; no word beside it, owner 2026-11-25), no site, then, with two or more vaults, the vault glyph (the app's vault symbol, an inline SVG) outside and to the left of a plain native pick list (`<select>`, accessible label "Vault") of the vault names, and, when the current vault is locked, a labeled **Unlock** beside it. The pick list shows only names, in the order the host reports, in the app's fixed order (no vault moves up because it is chosen, shown or open); an option is the name alone, with no padlock or other glyph, and states are said by the notice. Body, top to bottom: the notice (one at a time), the create or update card on a sign-up page, the search field with the pills directly under it, then "For This Site" above the card of this site's logins, then the footer. The second line of a row is the account, none when the name is the account. Nothing for this site: a notice in the vault notices' style, titled "No logins for this site", with "Passwords has none for this site. Search all logins above, or choose another vault." (the last clause only with two or more vaults; the popup never searches the other vaults for the person) and no button. On a sign-up page the update line reads "Passwords already has sam.r for this site." **Return** in the search field presses the one Fill there is: the only result of a search (either group), or the only login for the site when the field is empty. With two or more rows it does nothing. **Footer**: every state with the normal header ends with one labeled **Settings** button at the trailing end (it opens the extension's own settings page, see "Browser save prompt"), except Psss not running (no connection to the host), where the card is the whole popup. Safari's popup has no Settings button and no footer, because its manifest has no `privacy` permission and the settings page is not bundled.
- **Vault states.** `vaults` returns `[{ id, name, location, active, state, reason? }]` in the app's fixed list order (the shown vault is not moved first, and an open vault does not move up). `active` marks the vault the app shows; any number of vaults can be `open`. `state` is `open`, `locked` (Touch ID ready), `needs-password` (with `reason` `off`, `changed` or `locked-out`), `not-downloaded`, `not-found` or `unreadable`: the five states of the plan (`docs/vaults.md`), the same words as the app's menu and the AutoFill picker. The host cleans `name` and `location` with `DisplayText.safe` (no bidirectional controls, newlines or unbounded length) and the popup cleans again (`src/display.js`) and uses `textContent` only. The pick list lists names only (a native `<select>` cannot carry a location, a padlock or a warning glyph); the notice says the state. No Lock and no Add Vault… there: those are the app's.
- **Choosing a vault** (slice M2, 2026-11-25) changes the vault the popup lists, searches, fills from and saves into: it starts as the vault the app shows and every later request carries the chosen vault's `vault`. An open vault needs no unlock, and no other vault is locked. The popup also sends `switch-vault { vault }` so the app shows that vault too (Unlock works on it): it locks and unlocks nothing, and a refusal other than `not-found` does not stop the popup from using an open vault. The reply carries the new list and the header shows Unlock when the chosen vault is locked. If the chosen vault locks between the list and a click (a lock in the app), the host answers `locked`, the popup asks `vaults` again and shows that vault's notice with Unlock; nothing from another vault is shown or filled instead. The pure parts (pick list, which vault is chosen, notices) are `src/vaults.js`, tested in `tests/vaults.test.js`.
- **Unlock.** `unlock-vault { vault }` applies to the vault the app shows (`forbidden` for another one, so the popup sends `switch-vault` first when it has chosen a different vault; `not-found` for an unknown or over-long id). Touch ID ready: the host unlocks (the prompt takes focus and the browser closes the popup). Needs its password: the host asks Psss to come forward on that vault's lock screen (`ok` with `app: "opened"`, still locked) or, when it cannot, answers `needs-app`. `cancelled`, `failed`, `needs-app` and `not-available` each carry the new `vaults` so the popup draws the state as it is now. The vault button stays in every case, so another vault is one click away.

  | State of the current vault | What the popup says | Unlock |
  | --- | --- | --- |
  | locked | "Passwords is locked. Choose Unlock to use Touch ID." | yes |
  | needs-password | "Touch ID is off for Work." / "Touch ID changed since Work was set up." / "Touch ID is locked out right now." then "Unlock with the vault password." | yes: Psss comes forward, or "Open Psss to unlock Work." |
  | Touch ID cancelled or failed | orange: "Touch ID was cancelled." / "Touch ID did not work." then "Choose Unlock to try again." | yes |
  | not-downloaded, not-found, unreadable | orange: "Work was not found. Psss lists nothing from it here. Open Psss to locate it, or choose another vault above." (and "isn’t downloaded yet … to download it", "can’t be read … for details") | no |

  With one vault there is no vault button, so the notice carries Unlock. Nothing is listed, searched or saved while the chosen vault is not open, and the search field and create card are hidden.
- **The popup closes during Touch ID**, so the request goes through a background script (`background.js`, a service worker in Chromium, an event page in Firefox and Safari) that outlives it. On success it puts a check on the toolbar button, and the next click lists the vault's logins with no second prompt. On cancelled or failed it puts an orange exclamation mark and the next popup shows the "cancelled" notice. The popup clears the badge when it reads it. The badge holds only a symbol. Nothing about a vault, page or login is stored or logged. Without a background answer the popup asks the host itself.
- **Create a login** saves into the vault chosen in the popup. The button always reads "Generate, Fill and Save" (the header vault button names the vault). When the chosen vault already has this website and username the card says "Update a login", the line above the field says "Passwords already has sam.r for gitforge.example." and the button reads "Update Gitforge (sam.r)". The check uses the site's candidates in the chosen vault as the person types. Update changes only the password, never the username, title or website. `save` carries `vault`: the app (R4; the prototype host before) writes the named vault if it is open, and an update only for a login that the page's list just offered (otherwise `not-found` and the popup says it could not save), whichever vault the app shows (`locked` or `not-available` when it is not open, `not-found` for an unknown or over-long id), and the popup re-checks that the vault is still open before it fills anything. The create card is not shown while the chosen vault is locked.
- **App side.** `BrowserVaultSwitch` (`App/Core/BrowserVaultSession.swift`) is what the relay calls inside the running app: `vaults` gives each session vault's state (file problem, then open, then why a password is needed, from `VaultReference` and, for lockout, the app), `switchVault` runs `VaultSession.show` (nothing is locked), `items(vault:)` and `save(_:vault:)` read and write the open store the id names (nil or false when that vault is not open, so a vault locked since the list was read gives no data), and `unlockVault` goes through closures for the app's own Touch ID and for bringing Psss forward, so there is one shown vault and one unlock flow app-wide. `SessionVaultService` is the protocol's `BrowserVaultService` over a `VaultSession` (its calls run on the main actor; a login's reference is its item identifier). A save into a vault that is not the shown one registers that vault's AutoFill suggestions at once. Tested with real vaults in `Tests/KDBX/OpenVaultFilling.swift` (fill from a second open vault while another is shown, locked gives a notice and no data, a lock between search and fill, saves, a hostile name, no secret in any reply or state file) and on the prototype host in `Tests/Matching/main.swift` and `tests/host_test.py`.

**Decisions (2026-11-24, the plan's lead decisions, built).** The "Unlock" for a vault that needs its password asks the host to bring Psss forward on that vault's lock screen, and the notice says "Open Psss to unlock Work." when it cannot. Update changes only the password. Search is on top with the pills directly under it. Return fills the only match. The needs-password notice says why in a few words. The not-found way forward outside the app reads "Open Psss to locate it". Several vaults can be open at once and every request names its vault (protocol 4); the popup never falls back to another vault.

**Open, not solved.** (1) The relay is built as far as slices R1, R2 and R4 (see "Host and app"): the real app answers `ping`, `vaults`, `candidates`, `search`, `credential`, `generate` and `save` over the socket, so the popup lists the real vaults, fills from and saves into any vault that is already open. Every other request is answered `unsupported` by the app until the slice that adds it (unlock and bringing Psss forward: R3; cards are the prototype's samples only, so `card-candidates` and `card` stay `unsupported` in the app), so no real vault is unlocked from the browser yet and Psss never comes forward. The stand-in relay the tests run (Chrome, Firefox) models every state from `vaults.json` next to its prototype file: by default seven vaults (Passwords and Work open with Touch ID; Archive's Touch ID is cancelled; Family needs its password; Travel is not downloaded, Taxes cannot be read, Old is not found), and a test may write its own list (`vaults`: `id`, `name`, `location`, `file`, `quickUnlockOff`, `touchID`, `appComesForward`) plus `active` and `open` (the ids of the open vaults, any number; by default only the first is open, and a switch locks none). Passwords and Work have sample logins, any other vault only what is saved into it (`saved-logins-<id>.json`). (2) The Safari app extension relays to the app like the host (slice R5, “Safari over the relay”). Only while the app is not running does it answer for itself: `vaults` from the App Group (`StoredVaultService`: states from the stored references, every vault locked), `unlock-vault` by trying to start the app and otherwise `needs-app` (the popup says "Open Psss to unlock Work."), everything else `not-running`. (3) Not measured: whether the Mac app can show Touch ID for a vault chosen in the browser while it is not in front, whether it can be brought forward on a lock screen from the host (launch services from the host or a socket message to the app), and whether Touch ID lockout can be told apart from a cancel. (4) Not checked in Safari: that its event-page background script runs `action.setBadgeText` and wakes for the message (checked in Chrome and Firefox). ### Host and app

| | Now (slice R2, 2026-11-25) | Shipping design |
| --- | --- | --- |
| Chrome, Edge, Brave, Arc, Vivaldi, Firefox | `host/main.swift`, a relay client that Chrome or Firefox starts per message. It holds no key, no vault code and no file: it checks its caller, connects to the running Psss app over a Unix domain socket, checks that the app is signed by our team, sends the request and writes the app's reply back. The app serves `ping`, `vaults`, `candidates`, `search`, `credential`, `generate` and `save` from the real `VaultSession`; every other request type is `unsupported` there until R3. | The same, with the app also serving unlock (`docs/plans/browser-relay.md`). |
| Safari | `SafariWebExtensionHandler`, an app extension embedded in the Mac app, calls the same `BrowserProtocol` over the stored vault list. | The handler becomes a relay client of the same socket (slice R5). |

**The socket.** The app (macOS only) listens on `<App Group container>/Relay/browser.sock` (`~/Library/Group Containers/<TEAM>.app.psss/Relay/`). The `Relay` folder is mode 0700 and must be a real folder owned by the user (a link or a file there is refused, loose permissions are tightened), the socket is 0600, and the folder holds only the socket and `relay.lock` (no state). The app holds `flock` on `relay.lock` for its lifetime, so one copy serves: a second copy (a development build beside a release build) does not listen, a killed app's lock is released by the kernel, and only the holder removes a leftover socket file and binds. The path must fit `sun_path` (103 bytes plus the zero): otherwise the app does not listen and the host answers `not-running`. The server (`App/Features/BrowserRelayServer.swift`, Foundation only) runs on background threads and hops to the main actor for each request; `BrowserRelayLauncher` starts it once, from the first window's `.task`, once the `VaultSession` exists. It is a build without a team signature or App Group (an ad hoc build) that has no relay: the launcher reports `notSigned` and the host answers `not-running`. A line in Settings that says why the relay is off (another copy serving, path too long, not signed) is not built yet.

**Peer verification, both ways.** Before the app reads a byte it takes the connection's audit token (`LOCAL_PEERTOKEN`), asks the code-signing system for that process (`SecCodeCopyGuestWithAttributes`), and checks `anchor apple generic and certificate leaf[subject.OU] = "<TEAM>" and identifier "app.psss.native-host"`. Anything else is closed with no reply (the only log line is "peer refused" at debug level, with no path or process number). The host does the same to the app on its connected socket (identifier `app.psss.Psss`) and sends nothing unless it passes; if not, it answers `not-verified`. `anchor apple generic` accepts Apple Development, Apple Distribution and Developer ID certificates, so one requirement covers development, store and direct builds. The team is the one the process itself is signed with, read from its own signature at run time (an ad hoc host or app has none, so nothing is verified and nothing is served; this replaces the plan's "generated from the team id at build time" with the same effect and no generated file). What kind of caller it is comes only from the signature, never from the message. The tests' peer policy (`PeerPolicy.testing`, only under `HOSTLESS_TESTS` or `PSSS_RELAY_TESTING`) and the host's `PSSS_RELAY_SOCKET` (only with `-D PSSS_RELAY_TESTING`) are not in the shipping binaries; `build.py check` fails when the release host contains `PSSS_RELAY_SOCKET`, and the built app was scanned for the testing strings.

**Caller.** The host still checks its argument (the extension origin for Chrome, the add-on id for Firefox) against `allowed-callers.txt` next to the binary, and tells the app which one matched (`caller` in the envelope). The app checks it again against the ids compiled into it (`ExtensionIDs`, generated by `scripts/generate-extension-ids.mjs` from `extension-ids.json` and `targets/firefox.json`; the development extension id is known to debug builds only), so a changed text file cannot widen access.

**Framing and limits** (`App/Core/Relay/RelayFrame.swift`, shared by the host and the app). Browser to host is native messaging (4-byte native-endian length, JSON, at most 1 MiB). Host to app is a 4-byte big-endian length and UTF-8 JSON `{ "relay": 1, "caller": …, "request": { … } }`, one request per connection: connect, verify, one frame each way, close. The request is capped at 64 KiB and the reply at 1 MiB. The app gives 2 seconds to receive the whole request (one byte at a time does not extend it) and answers `timeout` after 5 seconds (`unlock-vault` 90, `save` 10; the host waits 2 seconds longer). At most 8 connections are open; the ninth is told `busy` at once and closed. The host only checks that the request is one JSON object and copies the bytes into the envelope; the app checks UTF-8, nesting depth (8), the envelope and `caller`, and `BrowserProtocol.handle` checks every field. A frame the app cannot take (length 0 or over the cap, malformed or non-object JSON, wrong `relay`, a bad `caller`) gets `unsupported`; a caller not on its list gets `forbidden`. If the host dies in the middle of a request the app sees end of file and drops the reply. Protocol 5 adds the errors `not-running` (nothing is listening, or the socket file has no listener), `not-verified`, `timeout` and `busy`, and `ping` says `app: true` when the app answered. The popup says "Psss is not open." for `not-running` and "Psss could not be verified." for `not-verified`; it has no Open Psss button yet (slice R3). A relay that closes without a reply (the app died, or refused the host) is `failed` ("Psss could not be reached.").

**Measured with team-signed binaries (2026-11-25, team 3549F795T2).** With a stand-in server signed as `app.psss.Psss` and the host signed with the team's Apple Development certificate as `app.psss.native-host`, both unsandboxed: the host listed the app's `ping` and `vaults`, the app served only the signed host, and a copy signed ad hoc (`not-verified`, it has no team), the same host re-signed under another identifier (closed, `failed`), an ad hoc test host aimed at the app (closed, `failed`) and `nc -U` (closed, no reply) were all refused. Quitting the app gave `not-running`. A process needs the `com.apple.security.application-groups` entitlement to create the `Relay` folder inside the group container (without it `mkdir` there is "Operation not permitted"), but the unsandboxed host needs none to connect to the socket. A sandboxed server (app sandbox plus the group entitlement, no profile) can bind and listen in the container, and the client can read its audit token and check its signature. What it cannot do is look at a peer whose executable lies in the user's home folder: `SecCodeCopyGuestWithAttributes` for such a host fails with "Operation not permitted", so the app refuses it. A host in `/Applications` or in `/private/tmp` is verified. So the sandboxed app can verify a host only where it may read it: inside `Psss.app` (the store design), or a system location such as `/Applications`, not `build/browser/host` under the home folder. For development the signed host is built into `/Applications/PsssDevHost` (`build.py host --sign … --output /Applications/PsssDevHost`, then `build.py install-host --host /Applications/PsssDevHost`). Measured with a bare signed stand-in, not with the real app (which has a provisioning profile and more entitlements): the signed run of the real app is the check.

**What the app answers in R4.** `ping` and `vaults`, from `SessionVaultService` over the app's `VaultSession` (names cleaned by `DisplayText.safe`, every vault's own state), and `candidates`, `search`, `credential`, `generate` and `save`. Touch ID lockout is not passed in yet, so a vault that is locked out shows `locked` rather than `needs-password` (reason `locked-out`) until R3 gives the service the unlock gate. `switch-vault`, `unlock-vault`, `card` and `card-candidates` are `unsupported`: an allowlist in front of the protocol (`BrowserRelayLauncher.servedTypes`; a relay test compares it with the list the tests assume).

- *Which vault.* A request names its vault (`vault`, at most 64 characters). It is read only if that vault is open in the app, whichever vault the window shows; a locked one answers `locked`, an unavailable one `not-available`, an unknown, missing or wrongly typed one `not-found`. Nothing is read from another vault instead, and nothing is switched, unlocked or launched by these requests.
- *The offer ledger* (`App/Core/Relay/OfferLedger.swift`). In memory only, keyed by (vault id, ref, host of the page), holding references and nothing else. `candidates` offers each matching login it lists for that page's host; `search` offers each result it returns (up to 20), the ones saved for other sites too, marked as searched. An offer lasts five minutes (the clock is injected, so the tests move it). The whole ledger is emptied when any vault locks or is removed (`VaultSession.onVaultClosed`, set by `SessionVaultService`), when the Mac sleeps or the display sleeps, when the screen locks and when the app quits (`BrowserRelayLauncher`); it is at most 1000 entries.
- *`credential`.* Checks, in this order: the vault is open (`locked` otherwise), the origin is fillable (`forbidden`: https, or http only for localhost and the loopback addresses, no user or password in the URL), the `ref` (at most 64 characters) names a login of that vault (`not-found`; a ref from another vault is not found), a login saved for another site is released only with `manual: true` (`forbidden`; only the JSON `true` counts, the number 1 or the text "true" do not), and the ref was offered for this page's host in this vault and has not expired, and a `manual` one was offered by a search (`not-found` otherwise). So a bare record id is worth nothing, the list shown for one page releases nothing on another, and Other Matches fills with one Fill and no sheet, only for a login that a search on that page returned (owner decision, 2026-11-25). A fill for the page's own site from an open vault asks nothing more: the click in the popup is the intent. The popup, if the answer is `not-found`, says "That list is out of date. Open Psss again."
- *`save`* (R4). Checks, in this order: the origin is fillable (`forbidden`: https, or http for localhost and the loopback addresses only, no user or password in the URL, a host of at most 253 bytes); the username (trimmed) is one plain line of at most 320 characters, with no control, format (bidirectional, zero-width, joiner), line or paragraph separator, private-use or unassigned character, and the secret is 1 to 1024 characters (`unsupported`: refused, never repaired, so what is saved is what the page asked for); the named vault is open (`locked`, `not-available` or `not-found` as for the other requests, and never another vault written instead). No prompt: the person pressed "Generate, Fill and Save" or "Update …". A login for this site and username that the vault does not hold is created (title the site's host, website the page's host). One it holds is an update, and only if the login was offered for this page in this vault within five minutes (the popup shows "Update …" from the `candidates` list, which offers it); otherwise `not-found` and nothing is written, so a bare site and username never overwrites a password the app has not just shown. An update changes the password only and the store keeps the old one in the item's history. If the vault locks between the check and the write, the answer is `locked` and nothing was written; a write that fails for another reason is `failed`. The save is one atomic file replacement on the main actor, one at a time: two saves at once are both written, and the same new login sent twice is one login (the second finds it, was never offered it, and answers `not-found`). The deadline is 10 seconds; a request that is still waiting for the main actor when it passes is dropped, never run afterwards. The saved login registers that vault's AutoFill suggestions (`VaultIdentities`) even when its window never saw it.
- *Secrets in transit.* A password crosses the socket in exactly three places: the reply to a successful `credential`, the reply to `generate` (the password is made in the app; the host holds no generator) and the `save` request (which the app answers with `result` and `vault` only). Lists, searches, errors, the vault list and every refusal carry none, whatever the vault holds; the relay test sends every type with known fixture secrets in the vault and scans each reply, the host's and the relay's output, the relay folder and the unified log. The app logs the request type and the error word only, never an origin, vault name, account or reference.

The host checks its caller twice. The browser enforces `allowed_origins` or `allowed_extensions`, and the host compares the argument the browser passes with `allowed-callers.txt`, which the installer writes. The host is signed with `-i app.psss.native-host`; the real relay needs the team's Apple Development identity (`build.py host --sign "Apple Development: …"`), an ad hoc host answers `not-verified`.

Prototype finding: Chrome starts a new host process for every `sendNativeMessage`, so references must survive process restarts. The host no longer derives references (the stand-in does, from website and account, because the sample vault makes new random item IDs on each launch). A real vault uses its stable record identifier. The AutoFill extension has the same constraint, since it resolves `recordIdentifier` in another process than the app that registered it.

### Safari over the relay

Slice R5 (2026-11-25). `SafariWebExtensionHandler` is a thin shell around `App/Core/SafariRelay.swift`, which uses the same client as the host (`App/Core/Relay/RelayClient.swift`): connect to `Relay/browser.sock` in the App Group container (found with `containerURL(forSecurityApplicationGroupIdentifier:)`, because the sandboxed extension has its own view of the home folder), check that the process that answers is the app (team and `app.psss.Psss`), send the message in the relay envelope, hand the reply back to Safari unchanged. The extension holds no key and no vault code.

- **Who is calling comes from the signature.** `PeerPolicy.signed()` accepts two kinds of peer, both signed with the app's own team: the native host (`app.psss.native-host`) and the Safari extension (`app.psss.Psss.Safari`, the signing identifier of the embedded appex). A native host may name only an extension id from the app's compiled list. A Safari peer may send exactly the caller `safari` and nothing else. Neither can claim the other's caller, and the message never decides the kind. The Safari kind gets the same message set as the host (the app's served types).
- **App not running** (connect fails): `vaults` is answered from the App Group (`StoredVaultService`, every vault locked), `unlock-vault` asks the system to start the containing app (`NSWorkspace.openApplication`, at most three seconds, only for this request, as the owner decided for the host) and answers `came-forward` if the system says it started, otherwise `needs-app`; every other request answers `not-running`. A build with no App Group container (signed only to run locally) has no socket and gets the same fallback.
- **Time.** The extension waits at most 10 seconds for the app plus 2 seconds of margin (a `save` is 10, everything the app serves today is under 5). The 90 second unlock is not served over the relay yet (R3), so nothing waits that long; R3 must measure how long Safari lets `beginRequest` wait and, if it is shorter, make the background script repeat the request after the badge. The handler logs the request type, the error word and the milliseconds (debug level, subsystem `app.psss`, category `safari-handler`) so the wait can be read from Console.
- **Checked** (R5): the relay harness runs the Safari client logic against the stand-in (`psss-relay-vault safari`): the signature names the kind, the caller is fixed, replies pass unchanged, the 64 KiB limit, and the fallback with no socket, a stale socket and no container. The signed build in `build/relay-dd` has the extension with identifier `app.psss.Psss.Safari`, team `3549F795T2` and the App Group `3549F795T2.app.psss`; a team-signed client with that identifier got `ping` (`app: true`) and the three real vaults' states from the running app, and an ad hoc copy was refused.
- **Not checked, needs Safari** (nothing here can drive Safari without the owner enabling the extension and “Allow Remote Automation”): that the sandboxed extension may connect to the socket (expected: a group container socket needs no entitlement), that `NSWorkspace.openApplication` is allowed from an app extension, how long `beginRequest` waits, and the popup in Safari end to end. The Mac’s `SafariExtensionReminder.extensionWorks` stays `false` until that has run.

## Requirements checked (2026-11-22)

- **Chrome Web Store.** [MV3 requirements](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements): all logic in the package, no remote code. The secure-handling rule does not apply to traffic between an extension and a native program on the same computer.
- **Chrome native messaging.** [Native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging): absolute `path`, `allowed_origins` without wildcards, manifest in the browser's user-data directory under `NativeMessagingHosts`, messages of at most 1 MB from the host.
- **Firefox.** [Native messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging): `allowed_extensions` holds the add-on ID, which must be set in `browser_specific_settings`. [Data collection](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/): `data_collection_permissions` is required for new AMO submissions from 2025-11-03, inside `gecko`.
- **Safari.** [Packaging](https://developer.apple.com/documentation/safariservices/packaging-a-web-extension-for-safari): `xcrun safari-web-extension-packager` (formerly the converter) reports unsupported manifest keys, and the build fails on any warning. [Messaging](https://developer.apple.com/documentation/safariservices/messaging-between-the-app-and-javascript-in-a-safari-web-extension): needs the `nativeMessaging` permission, only background scripts and extension pages may message the app extension, and an iOS app cannot message the extension's JavaScript.

How the end-to-end suites work, and the traps they hit:

- The test variant (`package --test`) is the production code plus localhost and `*.test` host permissions, `privacy` granted up front (automation cannot accept the permission dialog, so the dialog itself is checked by hand) and a small hook that points a popup opened as a tab at a tab by URL pattern. A popup in a tab has no active tab, and `activeTab` cannot be granted without a toolbar click, which automation cannot make. The real `activeTab` flow is therefore checked by hand with `--keep`. The test variant is never archived, and `check --test` allows nothing beyond those hosts.
- Branded Chrome ignores `--load-extension` (from version 137, and `--disable-features=DisableLoadExtensionCommandLineSwitch` no longer restores it in 158). The suite starts Chrome with `--remote-debugging-pipe --enable-unsafe-extension-debugging` and loads the extension with the DevTools command `Extensions.loadUnpacked`. Chrome for Testing accepts the same.
- A custom `--user-data-dir` makes Chrome look for host manifests inside that directory, so the suite registers the host there (`install-host --dir chromium=PROFILE`).
- Match patterns have no port. `http://localhost:8080/*` matches nothing in Firefox, so the hook uses `http://localhost/*`.
- Firefox 160 needs `MOZ_REMOTE_ALLOW_SYSTEM_ACCESS=1` for chrome-context scripts, and grants MV3 host permissions only through the person, so the suite grants them with `ExtensionPermissions`. Fixed `moz-extension://` addresses come from the `extensions.webextensions.uuids` pref.
- `*.test` names resolve to loopback with Chrome's `--host-resolver-rules` and Firefox's `network.dns.localDomains`, which lets the suites test non-local plain-HTTP hosts and lookalikes of `localhost` offline.

Ideas not built yet: HTTPS pages with a local certificate authority (the secure path), cross-origin and sandboxed frames, pages that swap the password field after load, two-step sign-in, a host that is slow or killed mid-reply, a running-app relay once it exists, and the Safari app extension on a simulator and a Mac.
