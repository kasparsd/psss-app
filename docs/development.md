# Native development

The product is named Psss. Xcode project, schemes, targets and bundle identifiers all use the name Psss and the reverse-domain prefix `app.psss`, after the domain psss.app.

Open [Psss.xcodeproj](../Psss.xcodeproj/project.pbxproj) in Xcode. Choose **Psss-macOS → My Mac** or **Psss-iOS → an iPhone or iPad simulator** and run. The app starts at a Welcome screen (create, import an Apple Passwords CSV, or try the sample vault). Try searching, narrowing by category or characteristic, opening, editing and deleting an item, and reviewing the Setup sheet (gear). Create a vault makes an encrypted KDBX file in the app’s storage, and Open a vault file edits a `.kdbx` in place. The iOS AutoFill extension opens the encrypted vault; the Mac provider is a stub. The sample vault is compiled in and kept in memory: nothing added to it is written anywhere. Use fictional inputs.

Brand icons are generated by `scripts/build-brand-icons.py` (Simple Icons, CC0 files, with a trademark caveat) into `App/Core/Assets.xcassets/Brands` and `App/Core/BrandIcons.swift`. The simulator's Face ID needs a manual match: `xcrun simctl spawn <udid> notifyutil -p com.apple.BiometricKit_Sim.fingerTouch.match`.

The project is maintained directly in Xcode. Synchronized source folders automatically include new Swift files. Shared settings live in `Configuration/Base.xcconfig`. Platform files hold SDK, deployment and sandbox settings. Both apps reuse `App/Core`, `App/Features` and `App/Bootstrap`. Separate extension targets compile `Extensions/CredentialProvider` and are embedded by Xcode. The workspace has no code generation step, package dependencies or shell build phases.

## Codec tests

```sh
scripts/test-kdbx.sh
```

Compiles `App/Core/KDBX`, the store and `Tests/KDBX/main.swift` with `swiftc` and runs them: RFC vectors for Blake2b, ChaCha20 and Argon2, round trips (AES and ChaCha20, key files, multi-block files, history, deletion), sessions (create, lock, unlock, conflict, overwrite, change password, backups) and interop with `keepassxc-cli` when installed. It is a stand-in until an Xcode test target exists. It writes only under `build/` and the app's Application Support folder, and cleans up its test vault.

## Other hostless tests

`scripts/test-format-swift.sh` compiles `App/Core/Format` (the Swift implementation of the [vault format](format-spec.md)), the first-party Argon2id and `Tests/Format/main.swift`, and runs them against the vectors in `Packages/format/vectors/`. It prints one line for every vector that fails, matches only in part or is skipped, and exits non-zero when any vector fails. `PSSS_HEAVY=1` adds the Argon2id vector that needs a gigabyte. The run writes `build/format-test/sealed-by-swift.json`, records and wrapped keys sealed by CryptoKit, and `scripts/test-format-interop.sh` opens them with the Node reference implementation (Node 24, no compile). `scripts/test-format.sh` runs the reference implementation's own tests.

`scripts/spike-sync.sh mac-mac|mac-iphone [rounds] [interval]` runs the CloudKit sync spike: two copies of the signed Debug app (two on this Mac, or the Mac and a paired iPhone) change the same item on a schedule and the script compares what each ends up holding. It needs signed builds in `build/sync-spike-dd`, both devices on one Apple Account, and the phone unlocked with Psss in front for the whole run. The harness is in `App/Core/Sync/SyncSpikeHarness.swift`, compiled in Debug only and inert without the `-psss-sync-spike` launch argument. It writes test records to zones named `spike-…` in the development environment of `iCloud.app.psss`. Do not stop Psss by name (`killall`, `pkill`) while a run is going: stop your own build by its path or process ID.

`scripts/test-matching.sh` checks site matching against the public suffix list, and `scripts/test-import.sh` checks the 1Password 7 importer against hand-written fixtures and, when present, a real export under `build/`. `scripts/build-public-suffix.py` downloads the list from publicsuffix.org and regenerates `App/Core/PublicSuffixList.swift`; commit the result. The codec and import scripts compile with `-D HOSTLESS_TESTS`, which drops the file-protection class from vault writes in those test builds only, because macOS refuses protected writes while the screen is locked. App builds keep complete file protection.
`scripts/test-safari-fill.sh` checks the card and address grant for iOS Safari (`App/SafariFill`, `App/Core/SafariFillSnapshot.swift`): what goes into it, which cards are left out, expiry, and the store against an in-memory Keychain stand-in. The real Keychain is not exercised.

`scripts/test-kdbx.sh` also compiles `-D HOSTLESS_UNLOCKGATE` and adds `App/Core/UnlockGate.swift` to the sources, which switches on the lock-notice checks at the end of `Tests/KDBX/main.swift` (a notice survives `didBecomeActive`, a timing lock clears a stale one). Without the flag those checks are not compiled.

Hostless builds never call the system's credential identity store. `VaultIdentities` (in `App/Core/KeePassVaultStore.swift`) forwards to `SharedVault` in app builds and records the calls under `HOSTLESS_TESTS`; tests read them with `VaultIdentities.takeCalls()`.
Every test process works in its own `run-<process number>` folders under the fixtures folder and under `PSSS_TEST_ROOT` and removes them at exit, so several copies of `build/kdbx-test/run` can run at once; always set `PSSS_TEST_ROOT`, or the tests write to the real app data. The in-memory Keychain stand-in (`BiometricKey.memory`) can make loads (`failure`) and saves (`saveFailure`) fail.

## Mac signing: local and provisioned

Without a development team Xcode signs the Mac app to run locally, and such a build cannot carry the AutoFill capability or a shared Keychain group. So the Mac targets use the `-local` entitlement files by default (`PSSS_MAC_ENTITLEMENTS_SUFFIX = -local` in `Configuration/macOS.xcconfig`). With a team and provisioning profiles, create an untracked `Configuration/Local.xcconfig` that sets `DEVELOPMENT_TEAM` and `PSSS_MAC_ENTITLEMENTS_SUFFIX =` (empty) to use the full files. In a local build the AutoFill provider cannot be enabled, and the vault and its reference stay in the app's own container. See [autofill](autofill.md#mac-builds-local-and-provisioned).

### Signed builds with a team

`Configuration/Local.xcconfig` is untracked and holds the per-developer values (use your own ten-character team ID):

```
DEVELOPMENT_TEAM = ABCDE12345
PSSS_MAC_ENTITLEMENTS_SUFFIX =
```

All targets use automatic signing, so with `-allowProvisioningUpdates` Xcode registers the App IDs (`app.psss.Psss`, `app.psss.Psss.CredentialProvider`, `app.psss.Psss.Safari` (Mac only)), the iOS App Group `group.app.psss` and development profiles for the team, and adds the connected device to the iOS profiles. Nothing else in the developer account changes. Always build through `scripts/xcb.sh`, which takes the `xcodebuild` arguments, runs one job at a time and keeps this Mac from running out of memory.

```sh
scripts/xcb.sh -project Psss.xcodeproj -scheme Psss-macOS -configuration Debug \
  -derivedDataPath build/signed-dd -allowProvisioningUpdates build

scripts/xcb.sh -project Psss.xcodeproj -scheme Psss-iOS -configuration Debug \
  -destination 'generic/platform=iOS' -derivedDataPath build/signed-dd -allowProvisioningUpdates build
```

Check the result with `codesign -d --entitlements - <app or .appex>`.

**Hotspot Configuration (iPhone and iPad app only, added 2026-11-24).** `App-iOS.entitlements` carries `com.apple.developer.networking.HotspotConfiguration` so Psss can offer “Join This Network” for a saved Wi-Fi network (`NEHotspotConfiguration`; the system asks the person first). The capability must also be enabled on the app's identifier: automatic signing in Xcode registers it on the first signed build; otherwise tick Hotspot Configuration under the App ID at developer.apple.com. Unsigned and `-local` builds do not carry it, so Join is hidden there. macOS has no equivalent: the Mac shows the QR code only.
Each Mac bundle must carry the AutoFill key (app and provider), `application-groups` and `keychain-access-groups` set to `<team>.app.psss`, a team identifier and `Contents/embedded.provisionprofile`.
Each iOS bundle must carry `group.app.psss` and `embedded.mobileprovision` (the AutoFill key on the app and provider).
The Mac provisioning profiles list the AutoFill capability and the keychain group `<team>.*` but no App Group: a team-prefixed group needs no profile entry on macOS 15 and later.
If the build says "PLA Update available", the account holder must accept the latest Program License Agreement at developer.apple.com; Xcode cannot create profiles until then.
A simulator build with the team set and no overrides builds, and Xcode embeds the simulated entitlements (AutoFill key and `group.app.psss`); the ad-hoc override recipe under "Testing AutoFill in the simulator" is then needed only for the temporary 26.2 floor.
The product is `build/signed-dd/Build/Products/Debug/Psss.app` (Mac) and `Debug-iphoneos/Psss.app` (iPhone, not installed by the build).

## The Psss folder in iCloud Drive

New vaults are kept in the app's iCloud container, shown as “Psss” in Files and Finder (`NSUbiquitousContainers` in `Configuration/App-Info.plist`). iOS reads that entry only when the app's build number changes, so an app first installed without it shows no folder until `CURRENT_PROJECT_VERSION` in `Configuration/Base.xcconfig` is raised and the app is installed over the old one. Confirmed on an iPhone 2026-11-24 (build 1 showed no folder, build 2 did). Raise the number whenever the entry changes. The folder can take a minute to appear. Builds without a team (the `-local` entitlements) carry no iCloud, so the create sheet dims “Keep in”.

## Command-line verification

```sh
xcodebuild -project Psss.xcodeproj -scheme Psss-macOS \
  -destination 'platform=macOS' -derivedDataPath /tmp/Psss-macOS \
  CODE_SIGNING_ALLOWED=NO build

xcodebuild -project Psss.xcodeproj -scheme Psss-iOS \
  -destination 'generic/platform=iOS Simulator' -derivedDataPath /tmp/Psss-iOS \
  CODE_SIGNING_ALLOWED=NO build
```

Reuse derived-data directories to keep incremental builds fast. Verify both schemes after shared changes. Check iPhone compact width and iPad regular width when editing navigation. Use Xcode for signing and archiving. Unsigned builds verify compilation and bundle assembly. Enabling a real credential provider requires registered identifiers, team profiles, and matching app and extension entitlements. See [AutoFill](autofill.md) and [release](release.md).

## Tooling outside Xcode

Custom tooling, build scripts, generators and reference implementations are written for Node 24 (decided by the owner, 2026-11-23), not Python. The same code can then be packaged as client libraries for working with vaults outside Apple platforms.

- `.nvmrc` pins the major version. Scripts find a Node 24 binary themselves and fail with a clear message when there is none; they do not assume the `node` on the path.
- `scripts/build-logo.mjs` builds the logo from one set of numbers: the files in `Design/Logo`, the landing page's inline logo and its CSS, and the drawing the mock pages use. Run it after changing the logo; see [brand](brand.md).
- TypeScript is run directly by Node (type stripping, erasable syntax only). No build step, and no dependencies unless a document records why one is needed.
- Code meant to become a library lives in `Packages/<name>/` with its own `package.json`, pure functions over bytes in the core and file system access in a separate module. The first is `Packages/format`, the reference implementation of the [vault format](format-spec.md). Every package under `Packages/` is a workspace of the root `package.json` (owner, 2026-11-24): run `npm install` once at the root (no dependencies, it only links them), then `npm test` runs every package's tests, `npm test -w @psss/vault` one of them, and `npm run start:sites` starts the [test sites](#test-sites-for-autofill). The `scripts/test-*.sh` wrappers stay for finding Node 24 and for the heavy-job lock. Packages still import each other by relative path. `Design/Mocks/app` and `Extensions/Browser/tests` have real dependencies and their own lockfiles, so they stay outside the workspace.
- The Python scripts that exist (`scripts/build-brand-icons.py`, `scripts/build-public-suffix.py`, `Extensions/Browser/build.py`) predate this and are ported when next touched.

## Design mocks

The interface mocks are being moved from hand-written pages into one React app, `Design/Mocks/app` (Vite, React, TypeScript, npm, Node 24). A phone, window or field row is drawn by one component, so a decision changes in one place instead of being copied across pages. Pages not yet ported stay static in `Design/Mocks/*.html`; `Design/Mocks/index.html` lists both.

- Open: `Design/Mocks/app/dist/index.html` straight from disk. It is committed, needs no server and works over file:// (relative base, hash routes such as `#/toolbar-and-edit`, one classic script and one stylesheet).
- Run: `cd Design/Mocks/app && npm install && npm run dev`. Build: `npm run build` (type-checks, then writes `dist/`). Commit `dist/` with the source change. `node_modules` is ignored.
- Add a page: write `src/pages/<Name>.tsx` from the page components (`Page`, `Clarity`, `Frame`, `DeviceView`, `Decisions`, `Against`), then add one entry to `src/registry.ts` with a short menu label. The route is `#/<slug>`, the home page lists it and the page menu at the top of every page links to it. Replace the old static file with a tiny page that links to the route (keep the file name so old links work) and point its `index.html` entry at `app/dist/index.html#/<slug>`.
- Components, one source of truth each (`src/components`): `IPhone` (status bar, iOS 26 tab bar with All / Codes / Cards and the detached search tab), `IPad`, `MacWindow` (traffic lights, optional menu bar); `DeviceView` with its per-view iPhone / iPad / Mac switch and `PageDeviceSwitch` for the whole page; `Workspace` (the Mac and iPad three-column layout, "Toolbar and Edit", interactive); `ItemCard` and `FieldRow` (icon above name, label above value, trailing copy icon, eight-dot mask with an inline eye, editor rows with Add code / Replace code / Remove code); `ListRow`, `CodeRow`, `CodesCountdown`, `CardEntry`, `EmptyState`; `InfoButton` with its reviewed topics; `UndoBanner`; the shared "Copied" pill (`CopyHost`). Sample data (logins with and without codes, a secure note, cards including one without a security code and one expired, items in Recently Deleted) is in `src/data.ts`; the iPhone screens are in `src/screens`.
- Dependencies: React, Vite and TypeScript only (owner request, 2026-11-23, for reusable mock components); no CDNs, no web fonts, no other packages.
- Conventions: system fonts and the system blue accent, light and dark by `prefers-color-scheme`, red only for deletion. Inside a device frame only two text sizes exist (17 px title, 13 px body). A decision about a row, button or bubble is changed in its component, never in a page. The pop-up row (a label on the left, a value or menu on the right) is `components/PopUpRow.tsx`, the drawing of `PopUpRow` in `App/Core/VaultSwitcher.swift`.

## Browser extension

`Extensions/Browser` holds the shared WebExtension (`src`, one flat folder), the native host and `build.py` (standard library only, output in `build/browser`). The Safari extension is built by Xcode: target `SafariExtension-macOS` bundles `Extensions/Browser/src` and `Extensions/Safari`, and the Mac scheme embeds it (the iOS app has no Safari extension). Chrome and Firefox archives, the host (a relay client: `App/Core/Relay` is shared with the app, and `App/Features/BrowserRelayServer.swift` is the app's side) and the tests come from `build.py` and `Extensions/Browser/tests`; `scripts/test-relay.sh` builds the test host and the stand-in relay and runs the relay harness, `host_test.py` and `build.py check`. After a change to `extension-ids.json` or `targets/firefox.json` run `node scripts/generate-extension-ids.mjs` (the app compiles the extension ids it accepts). `App/Core/BrowserProtocol.swift` answers extension requests for both the host and the Safari handler. Run `python3 Extensions/Browser/build.py check` after any change to the extension, and see [browser extension](browser-extension.md#build-and-try-it) for building, loading and tests (unit, host, and end-to-end suites for Chrome and Firefox; they need Node 22 or later and Python 3).

## Decisions

- Swift 6 language mode and explicit isolation at boundaries. Keep UI state on the main actor. Isolate document writes and run expensive KDF and parsing work outside the UI actor. Pass values across isolation boundaries with `Sendable` where applicable.
- Use platform-native SwiftUI on both targets. Prototype on the latest OS and SDK: deployment floors are macOS 27 and iOS 27 (Xcode 27.2). Decided 2026-11-22. Choose the shipping floor, probably one release back, from the AutoFill compatibility matrix in spike S3, and update `Configuration/*.xcconfig` then. This machine has iOS 18.6 and 26.5 simulator runtimes only, so install an iOS 27 runtime in Xcode to run the iOS app in a simulator. Until then, temporarily set `IPHONEOS_DEPLOYMENT_TARGET = 26.0` in `Configuration/iOS.xcconfig` to build for a 26.5 simulator, and restore 27.0 afterward. Unsigned simulator builds work without it.
- The shipping floor is iOS 26 and macOS 26 (decided by the owner, 2026-11-23). It is the first release with post-quantum key wrapping in CryptoKit, which the [vault format](format.md#decisions-for-the-owner) needs, and it runs on the iPhone 11 and later. The project still builds for 27 as the line above says; lowering the targets and adding fallbacks for 27-only interface code is open work.
- Use typed domain outcomes and map them to localizable messages in the view layer. Keep user-provided text verbatim. Use String Catalogs for translatable interface copy, and locale-aware FormatStyle and plural rules for dates and counts. Verify pseudolocalized string lengths and right-to-left layout as copy stabilizes.
- Keep development fixtures independent of real accounts, credential stores and user files. The prototype uses compiled sample items plus the unencrypted App Group store, and the provider fills from them.

## Testing AutoFill in the simulator

1. Start the test sites: `cd Packages/test-sites && npm start` (or the `test-sites` entry in `.claude/launch.json`), then open `http://localhost:8090`. See [test sites](#test-sites-for-autofill).
2. Build for the simulator with ad-hoc signing and a temporary 26.2 floor (the simulator has no iOS 27 runtime): set `IPHONEOS_DEPLOYMENT_TARGET = 26.2`, build with `CODE_SIGN_STYLE=Manual CODE_SIGN_IDENTITY=- CODE_SIGNING_ALLOWED=YES CODE_SIGNING_REQUIRED=NO DEVELOPMENT_TEAM=`, and restore 27.0.
3. Install, then enable Psss under Settings, General, AutoFill & Passwords. If it is missing, check that the app and extension both have the AutoFill entitlement, then run `xcrun simctl spawn <udid> pluginkit -e use -i app.psss.Psss.CredentialProvider` and restart Settings.
4. Open the test sites in Safari with the software keyboard enabled (turn off Connect Hardware Keyboard so the key icon shows). `/passkeys` creates a passkey and signs in with it, and the server verifies the signature. `/login` reproduces Google: it starts a conditional passkey request on load (username field `autocomplete="username webauthn"`, password field `current-password`). `/otp` asks for a verification code after the password, on `accounts.example.localhost` while the saved login is for `mail.example.localhost`. Save a login for `localhost`, open the page, choose Psss from the keyboard bar: the list must offer the login, and the passkey as well when one exists (create one on `passkey.html` first).

## Test sites for AutoFill

`Packages/test-sites` (Node 24, no dependencies) is a local server that plays any site's sign-in: sign-up with password rules, sign-in, change password, verification codes in every format (SHA1, SHA256, SHA512, 6 to 8 digits, 30 or 60 s), passkeys (create, sign in, conditional) and the same login on sibling hosts (`accounts.example.localhost`, `mail.example.localhost`). The server verifies codes and passkey signatures, so a pass means the provider is right. A JSON API sets up accounts and returns the expected code for scripts and agents. Run `npm run start:sites` at the root, `npm start` in the package, or use the `test-sites` launch entry (port 8090, seeded); test it with `scripts/test-sites.sh`. Details and limits in the package `README.md`. It replaced the Python `prototype/sample-site`. The browser-extension end-to-end suites start it themselves on port 8080 (`--port 8080`, Node 24) and open `/login.html` and `/signup.html`, which it serves as aliases of `/login` and `/signup`.

## Keychain on the simulator and Mac

Face ID unlock saves a key in the Keychain, which needs entitlements. Build the iOS simulator app ad-hoc signed: `xcodebuild ... CODE_SIGN_IDENTITY=- CODE_SIGNING_ALLOWED=YES CODE_SIGNING_REQUIRED=NO build`. An unsigned build (`CODE_SIGNING_ALLOWED=NO`) cannot save the key and Setup shows "Face ID could not be turned on". Enroll a face with `xcrun simctl spawn booted notifyutil -s com.apple.BiometricKit.enrollmentChanged 1 && xcrun simctl spawn booted notifyutil -p com.apple.BiometricKit.enrollmentChanged`. The Mac path uses the login keychain and works unsigned.
