# AutoFill and browser integration

| Surface | First route | Verification required |
| --- | --- | --- |
| iOS Safari and apps | AuthenticationServices Credential Provider Extension | Test inline suggestions, picker, locked continuation and save/update on chosen OS versions. |
| iOS Chrome, Firefox, Edge | System provider. These browsers use WebKit and iOS AutoFill, and extensions do not exist outside Safari. | Record fill and save independently on physical devices. Chrome offers its own manager first. |
| macOS Safari and apps | System provider and system AutoFill menu where exposed, plus the bundled Safari extension for generate and save on sign-up forms (macOS has no system API for them) | Compare inline, menu and picker. Run the extension in a signed build. What it adds is in [browser extension](browser-extension.md#safari-bundled-with-the-app). |
| macOS Chrome, Edge, Firefox, Brave, Arc, Vivaldi | Shared WebExtension plus native host, prototyped and tested in Chrome, Firefox and Zen in [browser extension](browser-extension.md). The system provider is expected not to reach them: confirm once with the provider enabled, and test passkeys, which these browsers may route through the system. | Record real fill, locked behavior and signed installation for each browser. |
| Other macOS browsers | Document tested system surfaces and manual copy fallback. | Test by browser, version and form type before advertising coverage. |

System integration uses `ASCredentialProviderViewController`, credential identity registration and save capability flags as supported by the deployment OS. Index minimal service metadata and stable opaque record references. Resolve a reference and recheck the request origin before releasing the credential. Refresh identities after edits, external changes, removal and access revocation.

The Safari extension is an app extension target embedded in the Mac app only, with its own native handler. Chrome and Firefox use browser-specific host registration and distribution; test sandbox compatibility with an archive-installed build before committing to the delivery path. The extension mediates the active page and asks native Swift code for the selected credential or a proposed save. Verify connection identity, tab and frame origin at request and delivery, enforce user intent, and keep secrets out of extension storage. Browsers may call different paths for filling and saving. Treat them as separate capabilities.

[Apple Credential Provider API](https://developer.apple.com/documentation/authenticationservices/ascredentialproviderviewcontroller), [Apple provider capabilities](https://developer.apple.com/documentation/bundleresources/information-property-list/nsextension/nsextensionattributes/ascredentialproviderextensioncapabilities), [Safari Web Extensions](https://developer.apple.com/documentation/SafariServices/safari-web-extensions), [Chrome native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [Firefox native messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging).

## Payment cards and other fields

AuthenticationServices documents a user-selected text insertion path. Verify it as a single-field option. Test multi-field checkout fill in browser extensions separately and restrict delivery to the selected checkout origin and verified fields. Keep card data and notes out of password suggestions. OTP uses the dedicated one-time-code request when supported.

[Apple provider APIs](https://developer.apple.com/documentation/authenticationservices/ascredentialproviderviewcontroller/), [Apple one-time-code AutoFill](https://developer.apple.com/documentation/authenticationservices/providing-one-time-passcodes-to-autofill).

## Decisions

- 1.0 covers Safari and apps through the system provider on iPhone, iPad and Mac. Other browsers on iPhone and iPad ride the system provider. Chrome, Edge, Firefox and other Mac browsers need the extension and native host in [browser extension](browser-extension.md), which is a prototype and stays out of 1.0 until its roadmap items are done.
- Bundle a Safari Web Extension with the Mac app. Its reason to exist is Mac generate and save on sign-up forms, and it shares one source folder and one protocol implementation with the Chrome and Firefox prototype. iPhone and iPad have none (removed 2026-11-24: it duplicated the system prompts); a card and identity filler for iOS Safari is a critical later feature. See [browser extension](browser-extension.md#safari-bundled-with-the-app).
- Passkeys and verification codes ride the same provider and are required for TestFlight.

- Prefer Apple’s integration anywhere it supports the intended action.
- Use a thin JavaScript adapter for WebExtension page interaction and Swift for native targets.
- Match conservatively across schemes, hosts, ports and frames. Keep manual selections explicit and revalidate on navigation.
- Matching rule (decided 2026-11-22, built 2026-11-23 in `App/Core/SiteMatch.swift` with the public suffix list generated into `App/Core/PublicSuffixList.swift`): a saved login is offered when its host equals the requested host, or the requested host is a subdomain of it. The subdomain case is refused, leaving an exact match only, when the saved host is a public suffix (`github.io`, `co.uk`), the parent of a wildcard rule (`compute.amazonaws.com`), a single label, a local name (`localhost`, `local`, `lan`, `internal` and the reserved test names), or an address (IPv4 in any spelling, IPv6). A login saved for a subdomain is never offered on its parent or a sibling. Hosts are compared after lowercasing, dropping a trailing dot and leading `www.` labels (kept when what remains is a public suffix), and converting international names to punycode. Anything malformed reads as no host and matches nothing: user info before the host, a backslash, `%`, whitespace or control characters in the host, empty labels, names over 253 characters, addresses with no network host such as `javascript:` or `file:`, a bare email address. An item whose website reads as no host is not registered with the system. An independent run of 362 adversarial cases found no way for a login to reach another party's site. `scripts/test-matching.sh` runs the suite and `scripts/build-public-suffix.py` refreshes the list (Mozilla Public License 2.0). `SiteMatch.related` (same registrable domain, not a match) is there for a later “related logins” hint.
- The scheme (built 2026-11-23, `App/Core/FillSite.swift`): when any service identifier the system passes is an `http` address for a host that is not this machine, the page counts as unencrypted. Its logins are then not offered automatically: they sit behind one labeled step and a confirmation that says anything filled can be read on the network. Limits: a suggestion picked from the keyboard carries only the stored domain, so the rule cannot apply there, and Safari may pass only a domain, in which case it never applies in Safari. Both need a signed build to find out.
- Showing a site name (`App/Core/HostDisplay.swift`): an international name is shown in readable form only when every part is made of letters, marks, digits and hyphens, is unchanged by Unicode's compatibility and lower-case forms, uses ordinary digits (or one non-Latin script with its own digits), and carries at most two accents per letter, each from the letter's own script and never an overlay. Anything else shows the encoded `xn--` form alone. A name that mixes scripts, or a Latin name with a letter outside the alphabets of European languages and Vietnamese, shows the encoded form beside it; Japanese, Korean and Chinese combinations count as one script. Matching always uses the encoded form. Known costs: every non-Latin name under a Latin ending such as `.com` shows the encoded form beside it, which is what exposes a Cyrillic lookalike of a Latin name; Turkish names with ı do too; and names in Yoruba, Igbo, Navajo, accented Lithuanian and stress-marked Russian show only the encoded form, because their accents have no single-character form.
- Showing text from the vault (`App/Core/DisplayText.swift`): a login's title and account are cleaned before the provider shows them. Direction-reversing, invisible, control and blank-rendering characters are removed, spaces collapsed, and the text cut to 80 characters as a person sees them (with caps of 8 accents per letter, 10 parts per emoji sequence and 320 characters underneath). The two zero-width joiners are kept between letters of the scripts that need them, such as Persian, Urdu, Hindi, Bengali and Malayalam. Nothing stored or filled changes.
- The confirmation before filling a login from another site, or on an unencrypted page, shows one fact per line with the sites first: “Saved for: …”, “You are signing in to: …”, “Login: “…””, “Account: “…””, “Only continue if you trust this page.” Values from the vault are in quotation marks and site names are not, so one cannot pass for the other. It is Psss's own sheet on iPhone, iPad and Mac, not a system alert, because the iOS 26 alert shows no preferred button for the default-action shortcut and a Mac alert cannot make Cancel both the Return default and the Escape button. Cancel is the default everywhere: a filled (prominent) button that answers Return. “Fill Anyway” is a plain bordered button, not red, because continuing is not a deletion. On iPhone and iPad the sheet is medium height (it can be pulled up) with the two buttons full width, Cancel first; on Mac Return and Escape both cancel.
- The provider's not-ready screen has one plain sentence per cause: no vault yet; Face ID or Touch ID not set up or no longer valid; the key cannot be used right now; the vault file cannot be found; the vault could not be opened.
- A keyboard suggestion opens the same list as the key button, for the suggestion's site (2026-11-24; owner: use the existing row format, always show the search): a matching login has the main Fill button, the search field and the Vault row (with two or more vaults) are there, and a code suggestion opens the code list the same way. The one-login Fill screen (`FillConfirm`) is gone. The code list and the text picker carry the Vault row too. After another vault is chosen the list for the site is shown. The provider also skips a second Face ID prompt when the vault is already open; the second prompt came from the request handler for a password suggestion calling `unlocked` again. Mock: `#/autofill`, frame A.
- Logins for other sites sit behind one labeled step in the fill list, and choosing one asks for a confirmation that names both the login's site and the current site. Today they are one tap away.
- Order of work is set by the [roadmap](roadmap.md#course-correction-review-of-2026-11-22): the real vault in the provider on a signed device first, then the Mac provider and verification codes. Interface polish waits for the M0 gate on 2026-12-20.

## Prototype status (2026-11-22)

- iOS 26.2 added `ASSavePasswordRequest` and `ASGeneratePasswordsRequest` for third-party providers. The extension implements fill list, fill confirmation, save sheet and generated passwords. Generated passwords honour the site's password rules (the three rule strings of the request are merged, and every offer satisfies them), and the save request for a filled generated password writes a login with no Name question, as the header asks, except when a login with that username already exists for the site: then nothing is written until the submit, which asks to Update it, so the old password stays until the site has taken the new one. On submit, a login that already holds the submitted username and password finishes without a screen, and a login saved earlier from the generated password without a username gets the username instead of a second login (`SaveMatch`, tested; a duplicate found in the simulator on 2026-11-25); `SupportsGeneratePasswordCredentialsWithUI` is `false` until Psss has its own sheet (see `plans/password-generator.md`). The iOS floor for 1.0 must be 26.2 or later if save and generate are required. macOS has no equivalent, so save and generate stay a platform gap (see `docs/roadmap.md`).
- `Packages/test-sites` serves sign-up, sign-in, verification-code and passkey pages at `http://localhost:8090` (`npm start` there; see [development](development.md#test-sites-for-autofill)). The Sample Site login in the sample vault matches `localhost`.
- Working in the iOS 26.5 simulator with ad-hoc signing (2026-11-22): the provider appears under Settings, General, AutoFill & Passwords once **both the app and the extension** carry `com.apple.developer.authentication-services.autofill-credential-provider`. - Verified in Safari against the earlier sample site (now `Packages/test-sites`): the keyboard key opens the provider chooser, our list shows “For localhost” first, Fill completes email and password, the system offers “Use Strong Password? - Passkeys verified in the simulator (iOS 26.5, the earlier `passkey.html` page, now `/passkeys` on the test sites): registration (`prepareInterface(forPasskeyRegistration:)`) and assertion (`prepareInterfaceToProvideCredential(for:)` and `prepareCredentialList(for:requestParameters:)`) both complete. ## Unlock (prototype)

- `Unlock.authenticate` in `App/Core/UnlockGate.swift` wraps `LocalAuthentication` with the `deviceOwnerAuthentication` policy: Face ID or Touch ID, falling back to the device passcode or Mac login password. The app and the extension share it.
- The extension authenticates before it lists, confirms, saves or signs: password fill, password save, passkey registration and passkey sign-in. Generating a password reads no vault data, so it does not ask. Cancelling returns to the system sheet. `provideCredentialWithoutUserInteraction` still asks the system for the interface, because a biometric prompt needs one.
- The app opens on a lock screen and prompts at launch and when it returns from the background. **Settings → Security → Lock** chooses Immediately, After 1, 5 or 15 minutes. **Lock Now** is in Setup on every platform, in the Mac and iPad “…” menu, and on ⌘L (Psss menu).
- Locking removes the vault view from the tree, so selection and search text do not survive behind the lock screen. Unlocking opens fresh with search focused.
- Policy follows Apple Passwords: authentication is always required and cannot be turned off; only the background timing is a setting. On Mac the vault also locks when the Mac sleeps, the display sleeps or the screen locks. See [experience](experience.md#lock-policy-follow-apple-passwords-2026-11-22).
- For the sample vault this is a user-interface gate only: it is not encrypted. A real vault is encrypted and opens with its vault password or, when switched on, with the Keychain key that Face ID or Touch ID releases, which has no passcode fallback. The always-on device-owner prompt described above applies to the sample vault.
- Simulator test: enroll Face ID with `xcrun simctl spawn booted notifyutil -s com.apple.BiometricKit.enrollmentChanged 1` and `-p` it, then send a match with `-p com.apple.BiometricKit_Sim.fingerTouch.match`.

## Platform facts checked 2026-11-23

From the iOS 27.2 and macOS 27.2 SDK headers on the development machine, and Apple's capability tables and developer forum answers where noted.

| Feature | iOS and iPadOS | macOS | Provider key |
| --- | --- | --- | --- |
| Password fill | 12 | 11 | `ProvidesPasswords` |
| Passkey sign-in and registration | 17 | 14 | `ProvidesPasskeys` |
| Verification codes | 18 | 15 | `ProvidesOneTimeCodes` |
| Automatic passkey upgrade | 18 | 15 | `SupportsConditionalPasskeyRegistration` |
| Text insertion (single fields, such as a card number) | 18 | Not available | `ProvidesTextToInsert` |
| Save password request | 26.2 | Not available | `SupportsSavePasswordCredentials` |
| Generate passwords request | 26.2 | Not available | `SupportsGeneratePasswordCredentials` |
| Credential exchange import and export | 26 | 26 | `ASCredentialImportManager`, `ASCredentialExportManager` |

- The AutoFill credential provider capability needs the paid Apple Developer Program on both platforms. App Groups and Keychain sharing alone do not.
- An App Group name works as a Keychain access group on iOS. On Mac it works only when a provisioning profile validates the entitlements, and `kSecAttrAccessGroup` is ignored outside the data protection keychain. So the Mac app and provider can share the Face ID or Touch ID key only in a provisioned build, and the unsigned Mac build proves the app alone.
- On macOS 15 and later an extension is denied the App Group container, with no prompt, unless the group ID is prefixed with the team ID, a profile authorises it, or the app comes from the Mac App Store.
- The identity store has password (iOS 12), passkey (17) and one-time code (18) identities, replace and incremental calls, and belongs to the system, so suggestions stay while the app is locked.
- A security-scoped bookmark made by the app does not resolve in the extension.
- Apple publishes no memory limit for the provider. Other KeePass apps report 64 to 120 MB. The provider's own budget for a typed vault password is in "The vault password in the extension" below; the device figures are still to be read from the log (S2).
- Chrome on iPhone and iPad documents using system providers; Edge and Firefox there are untested. No primary source shows Chrome, Edge or Firefox on Mac offering a third-party provider.

### Mac builds: local and provisioned

The Mac app, provider and Safari extension have two sets of entitlements. The local set is what a build without a development team can carry: sandbox, user-selected file access and bookmarks for the app, sandbox alone for the extensions. The full set adds the team-prefixed App Group, the AutoFill capability and the shared Keychain group, and needs provisioning profiles. `PSSS_MAC_ENTITLEMENTS_SUFFIX` in `Configuration/macOS.xcconfig` chooses, defaulting to `-local`; set it to empty, with the team, in an untracked `Configuration/Local.xcconfig`. A local build cannot enable the provider at all, keeps the vault in the app's own container, and keeps the Touch ID key in the login keychain behind the app's own prompt. A provisioned build uses only the protected Keychain item (current fingers only, this device only), never falls back, and removes leftover login-keychain items once. The provider on Mac only ever reads the protected item. A provisioned Mac build now exists (2026-11-23): all three Mac bundles are signed with the team, carry the AutoFill key (app and provider), the team-prefixed App Group and Keychain group `$(TeamIdentifierPrefix)app.psss`, and embed a provisioning profile. Nothing has been run from it yet, so the checklist below is still open for everything that needs the running provider. The iOS device build is signed and provisioned the same way, with `group.app.psss`.

### What only a signed device can settle

1. That the provider appears under AutoFill & Passwords with the paid team's profile, on iPhone, iPad and Mac, and that the Mac profiles carry the AutoFill capability, the team-prefixed App Group and the Keychain group for all three Mac targets.
2. Peak memory and unlock time in the extension on the oldest supported iPhone, for a small vault and one of a few thousand entries, on a cold start.
3. That the extension can read the biometry-protected Keychain item the app created, on iOS and in the Mac data protection keychain, and that the app's save of that item succeeds on Mac with no fallback.
4. That the Mac provider can open the team-prefixed App Group container, and that the group identifier resolves to the same value in the app, the provider and the Safari extension.
5. A document-scoped bookmark to an iCloud Drive file resolved from the extension, including after a restart.
6. The identity store when the provider is switched off, after a restart before first unlock, when the app registers against when the extension does, and whether one-time code identities are offered.
7. Whether Chrome, Firefox and Edge on Mac offer the provider, and Edge and Firefox on iPhone.
8. Passkeys on Mac in Safari and a native app, including automatic upgrade.
9. The Safari extension's handler reading the shared Keychain group, and how long a message through it takes.
10. Which Keychain errors really occur on a provisioned Mac (after fingerprints change, in a lockout), what the one-time removal of leftover login-keychain items does, and whether macOS prompts for it.
11. The provider's screens in the real system sheet on Mac: size, Return and Escape, whether Tab can reach “Fill Anyway” with full keyboard access, what VoiceOver announces, and the alert's default button on iPhone and iPad.
12. Whether the system passes a URL with its scheme, or several identifiers, so the `http` rule can apply; and whether the save and generate keys in the shared provider settings are ignored on Mac.
13. How right-to-left, very long and encoded site names and titles render in the confirmations.
14. Saving to a vault opened in place from iCloud Drive with the sandbox on, and a not-downloaded iCloud file being refused.
15. A site with a pending passkey request (Google, or `/login` on the test sites) offers the saved password, with and without a passkey saved, on iPhone, iPad and Mac, in Safari and in a native app.
16. On a simulator, which needs only the owner's approval of a device: a credential the extension saved is offered at once; the “not saved”, “not ready” and “can't save this passkey” screens; the sample vault session; the lock-screen and change-password wording.

## The picker (2026-11-24, owner)

One screen on iPhone, iPad and Mac, built in the app's own list style (owner, 2026-11-24; mock `#/autofill`). Each row is the app's `ItemListRow` (item icon, name, one line under it, the passkey glyph) with a visible bordered button at the trailing end: **Fill**, **Fill…** when it asks first (a login from another site, or on an unencrypted page), **Choose** for a card; the one login that is the default is prominent and answers Return. The second line is the account, or the website when the name is the account (`RowLine`). The heading above the logins (“For gitforge.example”) is a list header above the card, not a row inside it, in body size. The search field has focus when the picker opens. It is the system's field at the foot of the screen on iPhone and sits under the Vault row on iPad and Mac, and it searches the whole vault by name, username and saved site, A to Z, up to 40. While text is typed, **Name / Website / Username** capsule toggle buttons with counts (`SearchFieldPills`, accent when on, dimmed at 0) sit directly under the Vault row on iPhone and directly under the search field on iPad and Mac, with no gap above the list, and each row's second line shows the field that matched with the matching part bold (`searchSubtitle`); a website hit on a login that is not the page's own reads “Saved for …”, which may take two lines and is never cut. The counts and the narrowing come from `PickerSearch.counts` and `PickerSearch.matches(_:query:in:)`, which use the app's `ItemSearch` rule plus the host. Other items appear only once the person types, so nothing puts every login one tap away; choosing one from another site still shows “Fill a login from another site?”. With two or more vaults a site with nothing in the current vault says so under its heading: “No logins for cloudnest.example in Passwords. Choose another vault above.” Psss does not search the other vaults for the person. A footer under the list, outside its card, says “Tap a name to use one value instead.” (or “Showing 40 of N items. Type to narrow the list.” when it is cut; “Choose an item, then the value.” in the insert-text list). There is no single-login Fill screen on any path: a tapped suggestion, the key button and a passkey request all open this list.

**The browser extension popup takes the same style** (2026-11-24, mock `#/browser-extension`; details in [browser-extension](browser-extension.md#popup-style-search-and-vaults)): the same row (letter tile, name, username or matched field with the matching part bold, passkey glyph, a labeled **Fill** or **Fill…**) and the same Name / Website / Username pills with counts, with the search focused when the popup opens. Its vault control is the compact Vault button in the header (the name with ⌃⌄, no icon) with a labeled **Unlock** beside it while the current vault is locked, the same rule as the Vault row here (the popup half is the browser slice of the plan). Its create button always reads **Generate, Fill and Save**; the Vault button names where it goes, and it reads “Update Gitforge (sam.r)” when the current vault already has that website and username. The host decides which field matched, with the same `ItemSearch` rule as the app and picker.

The views the picker shares with the app live in `App/Core` (the extension compiles only that and `Extensions/CredentialProvider`): `ItemIcon`, `ItemListRow`, `SearchFieldPills` and the brand-icon asset catalog (`App/Core/Assets.xcassets`), so a brand's icon looks the same in the picker.

**The Vault row (owner, 2026-11-24; plan `docs/plans/vault-switcher-and-extension-style.md`, mock `#/autofill`).** One current vault per device: the app, this sheet and the browser popup all show it, and choosing another vault anywhere makes it current everywhere (`VaultSession.switchTo`, which works only while locked, so the open one is locked first). With two or more vaults every provider screen (login list, a login's values, code list, text picker, save password, create passkey, and every screen of a vault that is not open) has the shared `VaultRow` at the top: “Vault” and the current vault's name with chevrons opening the app's vault menu (every vault with where it is kept or its state, a check on the current one, the padlock or warning glyph; no Lock and no Add Vault…, which live in the app). Choosing a vault never closes the sheet. With Face ID or Touch ID ready it asks at once and lists that vault; on a values screen it returns to the new vault's list; on a save screen the form stays and only the destination changes. With one vault there is no row and the notice carries Unlock.

**Locked, needs password, not available.** When the current vault is not open the sheet shows the Vault row and one notice, not a dead end. *Locked* (quick unlock ready, the prompt was cancelled): “Face ID was cancelled.” and a labeled **Unlock** at the row's trailing end that asks again. *Needs password* (quick unlock off, lost or unavailable): “Face ID is off for Work.” / “Face ID changed since Work was set up.” / “Face ID is locked out right now.” and “Unlock with the vault password.”; Unlock opens the app's lock screen inside the sheet (`ProviderPasswordUnlock`): the Vault row, the vault password, a Key file row only when the vault is known to use a key file or after “Choose Key File…” in the wrong-password notice, “Checking your vault password…” while it runs, Unlock, and Cancel back to the notice. No More Options and no Forgot Password (the sheet cannot open the app). *Not available* (`VaultState`: not downloaded, not found, can't be read): a warning glyph in the row, no Unlock, and “Archive can’t be found. Open Psss to locate it.” / “Travel isn’t downloaded yet. Open Psss to download it.” / “Taxes can’t be read. Open Psss for details.” (`ProviderNotices`). The Mac provider needs `com.apple.security.files.user-selected.read-only` to choose a key file (added to both Mac provider entitlement files).

**The vault password in the extension.** The extension opens the file with the typed password through `VaultSession.unlock(credentials:savingQuickUnlockKey:beforeKeyDerivation:)`, and saves no Face ID key afterwards (the app does that after its own unlock). Argon2 asks for its whole memory parameter at once, so the extension reads it from the header before anything is derived (`KDBX.keyDerivationMemory(of:)`) and refuses with “Open Psss to unlock Work.” when it will not fit (`ExtensionUnlockBudget`): at most **64 MiB** on iPhone and iPad (the default of every new vault; larger vaults made elsewhere never fit) and only while `os_proc_available_memory()` has room for that plus 8 MiB, at most 512 MiB on Mac. Measured on a Mac (2026-11-24, optimized build, fresh process): one 64 MiB Argon2id derivation raises the peak resident size from 13 to 78 MiB and the footprint to 66 MiB, and the memory is returned afterwards. With an extension of roughly 40 to 50 MB under a limit of about 120 MB, a 64 MiB vault therefore fits with only a few MiB to spare, which is why the live check exists. Every password unlock logs the resident, peak and footprint sizes and the memory left (`app.psss.Psss`, category `unlock`, numbers only), so the device run (S2) can settle the number: read it in Console after one unlock on the oldest supported iPhone.

**Fill one field.** The system tells a provider the site, never which field is tapped, so Psss cannot aim a value. The person aims it: tap the page’s own field, then choose one value. Tapping an item’s name opens its values (login: username, password, verification code; card: number, name, expiry, security code). A login from another site, or on an unencrypted page, names both sites on that screen, which is the confirmation. Pure code: `PickerSearch` (search, value list) and `ReleaseCheck.value` (only the chosen value leaves the vault), tested in `Tests/Matching`. On iOS the only way to put a value into one field outside a password fill is text insertion (`completeRequest(withTextToInsert:)`, iOS 18 and later, from the text-insertion sheet), so the values screen opened from the picker list offers **Copy** (concealed, 60 seconds), not Use, until a device shows the system accepts an insertion from a list request. Mock: [fill-a-login.html](../Design/Mocks/fill-a-login.html), sections 3 and 4 and “The stories”.

- **Text insertion (iOS 18 and later):** `ProvidesTextToInsert` and `prepareInterfaceForUserChoosingTextToInsert` show `TextPicker`: search, open an item, **Use** inserts that one value into the tapped field with `completeRequest(withTextToInsert:)`. This is the route for a mislabeled form (a card number in a field called “Full name”). Not run on a device yet.
- **From the picker list:** whether the system accepts `completeRequest(withTextToInsert:)` from a password list request is unconfirmed, so the item screen says **Copy**, and the value goes to the clipboard (concealed, 60 seconds, local to the device) with a “copied” screen. Flip `insert` in `CredentialProviderViewController.prepareCredentialList` once a device shows it works.
- **Mac:** no call inserts a value, so Copy and paste.
- Left out for now: custom items (they have no mapped values in `fillValue` yet), notes and Wi-Fi networks.

## Passkey request list (2026-11-23)

- Sites such as Google start a passkey request as soon as the page loads (an autofill-assisted, conditional request). While it is pending, choosing Psss makes the system call `prepareCredentialList(for:requestParameters:)`, not the plain list, and Apple's header says that list shows “passkey and password credentials”. The first device run showed only “Choose a Passkey” and “No passkeys for this site yet.” with no way to fill the password.
- The list is the plain login list plus the passkeys, built by `PasskeyRequestList` (pure, tested in `Tests/Matching`). Passkeys for the request's relying party come first under “Passkeys for <rpID>”, honouring `allowedCredentials`, each row with the passkey glyph and **Sign In**. Then the logins saved for the page under “Logins” with “Fill”, with the same cross-site confirmation, plain `http` rule and cap of 40 as the plain list. Nothing puts every login one tap away. There is no warning paragraph: the system does not say whether the page also takes a password, so the logins stay listed and the list says nothing more.
- Passkey-only pages: the SDK does not say whether the page also takes a password. `ASPasskeyCredentialRequestParameters` (iOS 17, macOS 14, identical in the iOS and macOS 27.2 SDKs) has only the relying party, client data hash, user verification preference, allowed credentials and extension input, and no header in AuthenticationServices names a conditional or modal request for assertions ("conditional" appears only for passkey registration). So logins stay listed, because a sign-in page that asks for a passkey first but accepts a password matters most, and the list carries no warning about it. If the system gives none with a host, the request's relying party stands in as the site for matching logins (the browser has checked it against the page).
- Title “Sign In” when a passkey is listed, else “Choose a Login”. With nothing saved for the site: “No passkeys or logins are saved for <site>. Search to use another item.”, or with two or more vaults “No passkeys or logins for <site> in <Vault>. Choose another vault above.”, and the search on the same screen.
- **Why Google's passkey page offered none (investigated 2026-11-24).** The relying party is compared exactly with the stored `KPEX_PASSKEY_RELYING_PARTY`, and that is right: the request's `relyingPartyIdentifier` is the identifier the site chose (`google.com` for the sign-in page at `accounts.google.com`), the page host only picks the logins, and a looser match could not sign anyway because the signature covers the hash of the stored identifier. `Tests/Matching` pins `google.com` on `accounts.google.com`, a sibling identifier, case, trailing dot and `allowedCredentials`. The importers (Apple Passwords CSV, 1Password, CSV) carry no passkeys at all (a 1Password export holds none), so a vault imported from one has none to offer; that is the most likely cause, with `allowedCredentials` naming another provider's credential the other. The list now logs, per request, the relying party and counts only (passkeys in the vault, for this relying party, for a sibling identifier of the same domain, allowed credentials named, excluded by them, listed): read it in Console under `app.psss.Psss`, category `unlock`, after one visit to the page.
- One matching passkey and no login for the site still signs in without a list. If a login also matches, the list is shown, because the person may want the password.
- The same shared view serves iPhone, iPad and Mac.

## AutoFill state in the app (2026-11-23)

The app reads `ASCredentialIdentityStore.getState` at launch, after unlock and whenever it becomes active; there is no change notification. While AutoFill is off it shows a reminder card at the top of the list, above the title on Mac and iPad (Later snoozes it for 7 days, then it returns while AutoFill is still off), and Setup shows the state ([experience](experience.md#autofill-reminder-approved-2026-11-23)). When it finds AutoFill on after it was off, it re-registers the vault's identities straight away (`SharedVault.registerIdentities(for:knownEnabled: true)`), so logins saved while AutoFill was off are offered without the next unlock. An unsigned Mac build cannot enable AutoFill, so its card keeps returning after each Later and Apple's prompt never appears.

The state map (every state against the card, Setup and the empty vault) and the checks that keep the app matching it are on the mock page, sections 10 and 11 ([autofill-setup.html](../Design/Mocks/autofill-setup.html)).

## AutoFill without Face ID (2026-11-24)

One setting, on by default, no question (owner). Psss saves the vault's key after every password unlock, protected with `.userPresence`, so AutoFill asks for Face ID or Touch ID and falls back to the device passcode (the login password on a Mac). A vault no longer needs biometry to work with AutoFill, and a person cannot end up with neither. The provider types the vault password only when the sheet asks for it (a vault whose quick unlock is off or lost) and only within the memory budget under “The vault password in the extension”; it never saves a key from there. Setup's switch is "Unlock with Face ID or passcode"; turning it off deletes the key and AutoFill cannot open that vault until it is turned on. Cost: adding a face or fingerprint no longer invalidates the key, and anyone who knows the passcode can fill. Frames 25 to 29 on [autofill-setup.html](../Design/Mocks/autofill-setup.html), section 13. Not yet checked on a device: the system's passcode sheet in Safari, and the Mac provider is still a stub. Asking for it (2026-11-24, found on a device: Strongbox shows Face ID when AutoFill fills, Psss showed nothing and one code request failed with “Face ID or passcode is not available right now”): `BiometricKey.load` now asks for Face ID, Touch ID or the passcode itself with `LAContext.evaluatePolicy(.deviceOwnerAuthentication)` before the Keychain read, and reads the item with that evaluated context, so there is one prompt and a failure has a name (cancelled, no passcode, not available now) instead of an unnamed Keychain status. Not yet run on a device; the simulator shows the prompt and needs a manual match.

## Provider screen copy (2026-11-23)

- No vault, or only the sample vault: title “No vault yet”, body “Open Psss and create a vault. Then come back here to fill your logins. The sample vault is not available for AutoFill.” Every other case where the vault cannot be used has the Vault row and a notice (see “The Vault row”), never a dead-end screen.

## Save screens (2026-11-24)

“Save Password” (iOS) and “Create Passkey” (iPhone, iPad, Mac) show what will be saved (website, username, password or a new passkey) and one button that names what it changes: **Save**, **Update Gitforge (sam.r)** when the destination vault already has that website and username (the password changes, never the username, name or website), **Create Passkey**, **Add Passkey to Gitforge (sam.r)** when a login with that website and username has no passkey yet (a login that already has one is never overwritten; a new login is made). With two or more vaults the Vault row is at the top and the form survives a change of vault; a locked or unavailable destination shows its notice and the button stays dimmed until the vault is open. With one open vault a passkey is created at once, as before (the system sheet has asked already). Nothing is reported as saved to the system until the vault file was written (`SaveFailed` otherwise). **Saving happens once per request** (simulator, 2026-11-25: a second tap saved the login twice): the first tap dims the button and it reads “Saving…”, the provider ignores a second call, and the new login's id is made once per request, so even a repeated write is the same entry. The request completes when the vault file is written; the system's suggestion list gets at most 2 seconds more (the app registers every login again when it opens), and both times are logged to the `unlock` category (“provider save: …”). When the screen changes an existing login its title is **Update Password**, and a save button's title is plain text, never Markdown: “Update Gitforge (sam.r)”, or “Update Gitforge” when the login has no username. The title comes from the system's name for the site, made safe; the screen has no Name field.
